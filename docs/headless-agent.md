# Headless-агент разработчика (Cursor CLI)

Правило `.cursor/rules/headless-agent.mdc` описывает, как агент без интерфейса ведёт одно OpenSpec-изменение в контейнере разработки. Агента запускает Claude по ssh; общение идёт через файл статуса.

## Промпт запуска

```
Ты разработчик. Загрузи .cursor/rules/headless-agent.mdc. Задача: openspec/changes/<id>/, Jira <KEY>, task-id <task>.
```

Подстановки: `<id>` — каталог изменения, `<KEY>` — ключ Jira, `<task>` — идентификатор для `agent-state`.

## Команды обёрток в контейнере

- `agent-state get <task>` — прочитать состояние.
- `agent-state set <task> <состояние> [--message-file F] [--pr URL] [--patch PATH] [--artifact PATH]...` — состояния `working`, `question`, `review`, `committed`, `error`.
- Каталог задачи: `$AGENT_TASKS/<task>` (по умолчанию `/home/dev/tasks/<task>`); сюда же идут `change.patch` и `out/`.

## Цикл

1. `working` — разработка по `tasks.md`.
2. `question` — агент остановился с вопросом; ответ приходит продолжением сеанса.
3. `review` — сдан PR или `change.patch` и отчёт; в базу и хранилище агент больше не пишет. До `committed` или `error` задача держит тестовую базу: один контейнер ведёт одну задачу за раз, а ту же базу другой контейнер не получит (блокировка по `INFOBASE_PATH` из `.dev.env`).
4. Приёмка: продолжением сеанса приходит строка `ПРИЁМКА: принято, зафиксируй`; замечания возвращают в `working`.
5. `committed` — помещение в хранилище (комментарий `<id> <KEY>`) или слияние, тег и релиз; сборки cf / cfe / epf в `<task>/out/`. Статус принимается только после приёмки (`agent-reply --accept`), иначе `agent-state` отвечает кодом 4. Если есть и хранилище, и репозиторий, сначала хранилище, затем слияние, тег и релиз; сбой одной половины — `error` с описанием сделанного.
6. `error` — неустранимая ошибка, причина в файле сообщения.

## Инструменты базы и хранилища (vanessa-runner)

В Linux-контейнере агента PowerShell-скрипты `1c-metadata-manage` (`db-*`, `epf-*`) и `1c-repository-manage` (`repo-ops.ps1`) не исполняются. Их заменяет vanessa-runner 3.x: MCP-сервер `vrunner` в `.cursor/mcp.json` (в шаблоне выключен, в контейнере включается: `"disabled": false`) и та же утилита в оболочке, `xvfb-run -a vrunner …` (платформе нужен виртуальный экран).

Параметры подключения агент не задаёт сам: `agent-run` выставляет их из `.dev.env` проекта и файлов `~/.secrets` контейнера. Уже заданные переменные не перезаписываются.

| Переменная vrunner | Откуда |
|---|---|
| `VRUNNER_IBCONNECTION` | `INFOBASE_PATH`: при `INFOBASE_KIND=server` `сервер:порт/база` → `/Sсервер:порт\база`, иначе `/F<путь>`; значение, начинающееся с `/F` или `/S`, берётся как есть |
| `VRUNNER_V8VERSION` | имя каталога `PLATFORM_PATH` (`/opt/1cv8/x86_64/8.5.1.1343` → `8.5.1.1343`) |
| `VRUNNER_DBUSER` / `VRUNNER_DBPWD` | `IB_USER` / `~/.secrets/ib-password` |
| `VRUNNER_STORAGE_NAME` / `_USER` / `_PWD` | `REPOSITORY_PATH` / `REPOSITORY_USER` / `~/.secrets/storage-password` |
| `VRUNNER_EXTENSION_NAME` | `EXTENSION_NAME` |

Пароли в `.dev.env` контейнера не пишутся: `IB_PASSWORD` и `REPOSITORY_PASSWORD` оставить пустыми.

Ограничения, проверенные на БП 3.0 / 8.5.1:

- Операции Конфигуратора (загрузка и выгрузка, обновление БД, хранилище, сборка) идут без окон.
- Операции Предприятия (список и проверка расширений, тесты YAxUnit/Vanessa, свойства расширения после загрузки) могут зависнуть на модальном окне БСП: «Предупреждение безопасности» при первом входе пользователя с правом открывать внешние обработки, окна первого запуска после изменения конфигурации. vanessa-runner формирует `/C` сам и не передаёт `ОтключитьЛогикуНачалаРаботыСистемы` (issue vanessa-opensource/vanessa-runner#378). Первый вход пользователя агента делает человек и закрывает окна.
- MCP-инструменты `cfe_*` (vrunner 3.0.2) не берут имя расширения из `VRUNNER_EXTENSION_NAME` и без явного `extension_name` работают с основной конфигурацией: `cfe_unload` выгрузил всю конфигурацию БП вместо расширения. Утилита в оболочке переменную учитывает. Правило агента требует передавать имя явно.
- Прерванный запуск оставляет сеанс в кластере, который блокирует обновление БД: после тайм-аута завершать свои сеансы.

## Применение патча на стороне архитектора

Патч делается как `git add -A && git diff --cached --binary > change.patch`, поэтому содержит новые файлы и бинарные изменения. Применять к «было» (чистая выгрузка или основная ветка):

```
git apply --index --binary change.patch
```

`--index` переносит изменения и в индекс (новые файлы попадут в коммит). Бинарные блоки разбираются из патча, сделанного с `--binary`. Проверка без применения: `git apply --check change.patch`.

## Файлы

`.gitattributes` приводит переносы строк к виду платформы (`*.bsl`, `*.xml` — CRLF) и скрывает `ConfigDumpInfo.xml` из diff, чтобы разница на приёмку содержала только значимые правки.
