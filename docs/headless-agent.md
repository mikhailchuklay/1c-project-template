# Headless-агент разработчика (Cursor CLI, Codex CLI)

Правило `.cursor/rules/headless-agent.mdc` описывает, как агент без интерфейса ведёт одно OpenSpec-изменение в контейнере разработки. Агента запускает человек или архитектор (Claude, другой агент) по ssh; общение идёт через файл статуса. Контейнеры агентов универсальные (`dev-agent1`, `dev-agent2`, …; до 21.11.2026 — `dev-agent-cursor1`/`-codex1`/`-dsh1` по харнесу): в каждом есть все три харнеса — `cursor` (Cursor CLI, MCP из `.cursor/mcp.json`), `codex` (Codex CLI, MCP из `.codex/config.toml`) и `dsh` (DeepSeek Harness со слоем 1С, MCP из `.dsh/agent.env`). Харнес задачи выбирает архитектор при запуске: `docker exec -e AGENT_HARNESS=<харнес> dev-agent<N> agent-run …`; без `-e` — харнес контейнера по умолчанию. `agent-run` записывает харнес в статус задачи, `agent-reply` продолжает чат на нём же. Рабочее дерево задачи (`git worktree`) локальных файлов базового клона не наследует — копируй файлы MCP выбранного харнеса (для dsh — `.dsh/agent.env` и `.mcp.json`, иначе бандл ищет серверы на `127.0.0.1:800N` и отвечает `MCP_LOCAL_NOT_RUNNING`). Обёртки `agent-run`, `agent-state`, `agent-reply` одинаковы для всех.

## Выбор исполнителя — зона архитектора

Какому харнесу и в какой контейнер поручить задачу, решает архитектор сам, без согласования с владельцем. Контейнер и харнес выбираются независимо: любой харнес запускается в любом свободном контейнере. Владелец не выбирает исполнителя и не подтверждает выбор; он только сообщает ограничения (например, у харнеса закончились лимиты), и архитектор их учитывает до отмены.

Критерии, по порядку:

1. **Доступность.** Контейнер свободен (`agent-state` его задач не в `working`/`question`/`review`), у выбранного харнеса есть лимиты и баланс, MCP 1С и локальные файлы рабочей копии для этого харнеса на месте.
2. **Очередь и стенд.** Не нарушать согласованную очередь работ и блокировку тестовой базы (`agent-run` откажет при занятой `INFOBASE_PATH`). Как развести задачи по стенду — см. «Планирование стенда» ниже.
3. **Эффективность — выбор харнеса под задачу.** Минимум токенов, денег и кругов ревью при том же качестве: харнес, который лучше справлялся с похожими задачами (`tools/task-board.sh scorecard`), и тот, что уже вёл соседнюю задачу (продолжение чата, контекст), лучше холодного; аудит и спецификацию без записи на стенд можно отдать более дешёвому харнесу, сложную реализацию с прогонами на стенде — сильнейшему из доступных. Кончился лимит или баланс одного харнеса — задачу можно запустить на другом в том же контейнере.

### Запасная модель Cursor при исчерпании лимита

У Cursor лимит считается по модели и общий на аккаунт: сильная модель (Grok и подобные) может кончиться сразу во всех контейнерах, режим `auto` остаётся доступен. Решение владельца 22.11.2026: **когда основная модель Cursor недоступна (ответ «You're out of usage», лимит, отказ модели), агент работает на `auto`**, задача не встаёт и вопрос владельцу не выносится.

- Упавший ход продолжается в том же чате: `agent-reply … --model auto` (харнес тот же, `AGENT_HARNESS=cursor`). Новая задача, пока лимит не вернулся, запускается с `--model auto`.
- На доске `model=auto`. В ретро задачи строка «Исполнитель: cursor/auto — подошёл / не подошёл: причина» и отметка, что это запасная модель.
- Ревью хода на `auto` строже обычного: бенчмарк у неё ниже. Сложную реализацию с прогонами на стенде можно вместо `auto` отдать другому харнесу по критериям выше. Если это платный харнес, его стоимость указывается в отчёте.
- Когда основная модель снова доступна, следующая задача возвращается на неё: резолвер последней модели в образе выбирает её сам.
- Автоматическое переключение на `auto` внутри обёрток — задача образа агентов (1commerce-infra #129). До её выкатки переключает архитектор.
- **Порядок исполнителей при исчерпании лимитов** (решение владельца 22.11.2026):
  1. Cursor, основная модель (последний Grok).
  2. Cursor `auto` — простые задачи, доработки, спецификации.
  3. dsh (DeepSeek по API, платно) — сложная реализация с прогонами на стенде, а также любая задача, если и `auto` отвечает «out of usage». Стоимость указывается в ретро и на доске (`task-board usage`).
  4. codex — только с разрешения владельца: он расходует личный лимит владельца.
- Именные модели внутри Cursor (Claude, GPT, Gemini и другие) берут лимит из тех же пулов, что и основная модель. Когда пул исчерпан, переключение на другую именную модель Cursor не помогает, переключаться надо на `auto` или на другой харнес.
- Тариф Cursor и оплату сверх лимита (on-demand) архитектор не меняет и не предлагает менять без причины. Тариф старый (legacy), и при смене можно потерять действующие условия `auto`.

### Переоценка харнесов и моделей

Исполнитель — это пара «харнес + модель». Выбор по умолчанию не вечный: архитектор переоценивает его по регламенту, без команды владельца.

- **Когда.** (1) Раз в неделю вместе со `scorecard`. (2) Появилась новая модель или версия у харнеса (`cursor-agent --list-models`, новые модели DSH/Codex) или новая редакция внешнего бенчмарка 1С. (3) Ретро задачи показало, что трение — от исполнителя: ≥2 круга ревью из-за качества агента, повторяющиеся ошибки одного рода, зависания, лимиты. (4) Владелец сообщил новое ограничение (лимит, тариф, баланс).
- **Чем.** Факты своего проекта: `tools/task-board.sh scorecard` (группировка «харнес / модель»; модель пишется на доску `model=<id>` при запуске). Внешний бенчмарк 1С: https://vibecoding1c.ru/bench — баллы на задачах 1С с MCP и без, цена за токены. Цена для владельца: подписка без лимитов — нулевая предельная цена; подписка, которую владелец делит со своей работой, — расход его лимита; API — деньги за токены. Свои факты весомее бенчмарка; бенчмарк — для моделей, которых в проекте ещё не было.
- **Как решать.** Модель по умолчанию — лучшая по бенчмарку и фактам среди доступных без ущерба для владельца; дешёвый или ограниченный харнес — по причине (второе мнение, сбой основного, простая задача). Новую модель сначала даёт одна задача среднего риска, решение о переходе — по её ретро. Смена модели по умолчанию — правка образа или конфигурации агентов (зона техархитектора), со ссылкой на основание.
- **Где фиксировать.** В отчёте недели — сводка и решение («оставил / сменил X на Y, основание»). В ретро задачи — строка про исполнителя (см. «Ретро» ниже). Текущие ограничения владельца по харнесам — в памяти проекта.

Выбор контейнера и харнеса и причину архитектор фиксирует в своём отчёте и на доске (`executor=<N> harness=<харнес> model=<модель>`); перенос задачи на другой контейнер или харнес — тоже его решение. Продолжить чат задачи можно только на харнесе её запуска; смена харнеса — новый прогон под новым именем задачи с переносом изменений (как при лимите: снимок и `diff.patch`).

## Обновление правил из шаблона

Правила, навыки и скрипты агентов приходят из шаблона [1c-project-template](https://github.com/mikhailchuklay/1c-project-template) через `/updaterules` (`tools/update-from-template.sh` / `.ps1`); версия проекта записана в `.rules-template-sync.json` (`commit`). Шаблоном пользуются несколько проектов, в том числе невидимые его авторам, поэтому проект забирает обновления сам, а шаблон отвечает за совместимость и описывает каждое изменение в `CHANGELOG-TEMPLATE.md` (пометки `[несовместимо]`, `[безопасность]` и что делать проекту). `tools/update-from-template.sh --check` ничего не меняет и отвечает кодом: 0 — правила актуальны, 1 — проект отстаёт (число коммитов и строки журнала с пометками), 2 — ошибка проверки.

Синхронизация — зона архитектора: запускает сам или поручает, без указаний владельца. Она идёт отдельной веткой и PR (`chore/updaterules-<дата>`, у автоматики — `template-sync/<ветка>`); архитектор проверяет diff (затронуты только синхронизируемые файлы; `.dev.env`, `memory.md`, `USER-RULES.md`, `LLM-RULES.md`, `src/` не тронуты) и сливает сам.

- **(а) Перед `agent-run` новой задачи или нового этапа** — `tools/update-from-template.sh --check` в основной копии проекта. Код 1 — сначала синхронизация, потом запуск. Синхронизацию делает один исполнитель: автоматика шаблона (если проект подписан), архитектор или отдельная задача агента, поставленная только на `/updaterules`. Агенты задач разработки синхронизацию сами не делают: параллельные контейнеры дают дубли PR, а правки правил смешиваются с PR фичи. Код 2 — разобраться с причиной (сеть, нет `.rules-template-sync.json`), запуск не блокируется, проверку повторить.
- **(б) Задачи в работе на новые правила не переводятся**: агент живёт по правилам на момент старта и подхватит новые при следующем этапе или ребейзе на `main`. Исключение — записи журнала с пометкой `[безопасность]` или `[несовместимо]`, которые ломают инструменты задачи: тогда архитектор сливает синхронизацию в `main` и пишет агенту `agent-reply` — влить свежий `main` в ветку задачи и что изменилось; решение и причина — в ретро задачи.
- **(в) Еженедельно**, вместе со `scorecard` и переоценкой исполнителей, — `--check` во всех проектах архитектора; отставание и принятое решение — в отчёт недели.
- **(г) Закрепление версии.** Проект может закрепить ветку, тег или коммит шаблона ключом `RULES_TEMPLATE_REF` в `.dev.env` (`--check` и синхронизация берут его вместо `master`); снимать закрепление — после разбора записей журнала с пометками.
- **(д) PR в шаблон** добавляет строку в `CHANGELOG-TEMPLATE.md` и описывает в PR влияние на проекты: что сломается или изменится и что делать проекту. Несовместимое изменение — с переходным периодом (старое имя, ключ или вызов работает с предупреждением) и сроком перехода в журнале. Метка `[skip ci]` в заголовке PR шаблона откладывает автосинхронизацию подписчиков до следующего слияния или ручного запуска workflow.

**Автосинхронизация (добровольная подписка).** Проект может подписаться строкой в `consumers.json` шаблона (`repository`, `branch`, `autoMerge`, необязательно `templateRef`). При слиянии в `master` шаблона GitHub Action `template-sync` запускает синхронизацию в клоне подписчика и открывает или обновляет PR «/updaterules». Автослияние — только если подписчик указал `autoMerge: true`, изменены лишь файлы, которыми владеет шаблон, и нет пропусков из-за местных правок (например, свой `.gitattributes`); иначе PR ждёт архитектора проекта. Токен — секрет `TEMPLATE_SYNC_TOKEN` репозитория шаблона, его заводит владелец; без секрета действие только предупреждает.

## Планирование стенда — зона архитектора

Очередность задач на общей тестовой базе архитектор решает сам, без согласования с владельцем: ставит в очередь, запускает параллельно или выносит на временную копию. Владелец задаёт только приоритеты и запреты. Архитектор учитывает их до отмены и согласует очередь с архитекторами соседних задач через доску задач (ниже), а не сообщениями между сессиями.

| Ситуация | Решение |
|---|---|
| Обе задачи только читают базу | Параллельно (`--force-parallel`), причина в промпте. |
| Блокировку держит задача, которая только читает (аудит, спецификация); вторая пишет в свои технические документы и загружает расширение | Допустимо параллельно (`--force-parallel`). В промпте писателя: чужие документы не трогать, расширение загружать минимальное число раз (в идеале один, на итоговой сборке), время загрузки — в протокол, чужие сеансы не завершать (только `question`). Архитектора читающей задачи предупредить заранее: что изменится в API после загрузки. |
| Две задачи пишут, особенно в одни объекты метаданных, регистры или модули, либо меняют настройки базы | Очередь. Если задача нужна раньше очереди — временная копия базы. |
| Нужна проверка обновления с прошлого релиза, разрушительный эксперимент или массовая запись | Временная копия базы. |

**Временная копия.** Создаётся через Devbox только как временная: `infobase.copy temp=true issue="<репозиторий>#<N>" ttl_days=7` (продление — `infobase.temp-extend`; клиент со старой схемой MCP — прямой `tools/call`), с публикацией, аналогичной исходной: HTTP-сервисы API и MCP данных, те же учётные записи API. Сразу после создания — запись на доске: `tools/task-board.sh claim <имя-копии> --holder <сессия> --issue <N> --ib <id базы> --pub <адрес>… --temp`. До запуска агента сними окно БСП «Информационная база была перемещена или восстановлена из резервной копии»: копия получила новую строку соединения, и первый интерактивный запуск (тонкий клиент, тесты в режиме Предприятия) ждёт решения в модальном окне — на #73 1c-integration-api-bp агент повис на нём. Штатный способ БСП — серверная процедура `РегламентныеЗаданияСервер.ЗаблокироватьРаботуСВнешнимиРесурсами()` (БСП 3.1, «Базовая функциональность»; то же, что кнопка «Это копия» в окне): выполни её на копии через `tools/dev-standalone/Invoke-DataMcp.ps1 code` или внешнее соединение. Решение сохраняется в базе, окно больше не открывается, а регламентные задания и обмены копии не ходят во внешние системы (переопределение `ПриЗапретеРаботыСВнешнимиРесурсами`). Если задаче нужны внешние ресурсы копии — `РегламентныеЗаданияСервер.РазблокироватьРаботуСВнешнимиРесурсами()`, и это решение архитектора с причиной в промпте. Проверка — запуск клиента копии с тайм-аутом без окна. В промпт агента — адрес копии и её `INFOBASE_PATH`. Копия создаётся под задачу и удаляется после успешной проверки: `infobase.drop` — временную копию её создатель удаляет **без подтверждения владельца**, публикации (в том числе `-mcp`) Devbox снимает сам; затем `tools/task-board.sh release <имя-копии> --holder <сессия> --drop`. Идентификаторы базы и публикации архитектор записывает в отчёт и память до удаления. Копия не подменяет приёмку на основном стенде, если её требует DoD. Копия наследует то, что стоит на общем стенде в момент клонирования, в том числе невыпущенную сборку чужой задачи: снимок «до правок» снимай на последнем релизе, загрузив его актив на копию первой загрузкой (19.11.2026, #98 1c-integration-api-bp: на клоне acc-demo оказалась сборка 1.57.0 до её релиза). Очередь заданий Devbox последовательная: копия может часами ждать за чужой долгой операцией — проверь `jobs_get` сразу и планируй работу без базы на это время.

Решение и причину архитектор фиксирует в отчёте и на доске задач; архитекторы соседних задач видят его там.

## Доска задач — `tools/task-board.sh`

Одна доска на проект: `<основная копия>/.task-board/board.json`, вне git (путь в `.gitignore`). Сессии из рабочих деревьев пишут в тот же файл (основную копию скрипт находит через `git rev-parse --git-common-dir`), каждая запись идёт под `flock`. Доска заменяет согласование стенда сообщениями между сессиями.

- **Очередь работ:** issue, приоритет, архитектор-сессия, исполнитель (контейнер и харнес), стенд/база, состояние — `tools/task-board.sh set <issue> priority=1 architect=<сессия> executor=1 harness=codex stand=acc-demo state=working`.
- **Занятость стендов и временных копий:** id базы, публикации, кто держит и с какого времени — `claim <стенд> --holder <сессия> [--issue N] [--ib ID] [--pub URL] [--temp]`, `release <стенд> --holder <сессия> [--drop]`. Стенд занят другим — `claim` отказывает с кодом 1 и называет держателя: договариваешься с ним, а не загружаешь поверх.
- **Карточка задачи:** круги ревью, прогоны агента, время, токены и $ агента (если харнес их отдаёт), хотфиксы после релиза — `inc <issue> review_rounds|agent_runs|hotfixes`, `usage <issue> <N> <задача>` (или вручную `set <issue> tokens=… cost_usd=…`), `card <issue> [--markdown]`.

Правила:

1. **Перед запуском агента и перед загрузкой на стенд** — `tools/task-board.sh list`, затем `claim` стенда (или копии). После `agent-run` — `inc <issue> agent_runs`; каждый возврат агенту замечаний — `inc <issue> review_rounds`; хотфикс после релиза — `inc <issue> hotfixes` у исходной задачи.
2. **Освобождение:** после `committed`/`error` и загрузки релиза — `release`; удалённая копия — `release --drop`. Освобождает архитектор в своей основной копии: у агента в контейнере свой клон и своя доска, его `release` до доски архитектора не доходит (19.11.2026, #98 1c-integration-api-bp: агент «освободил» acc-demo, а доска архитектора держала стенд занятым).
3. **Закрытие issue:** сначала расход агента — `tools/task-board.sh usage <issue> <N> <задача>` по каждой задаче агента этого issue (токены, `cost_usd` — реальные деньги, у подписки 0; `api_equiv_usd` — эквивалент по прайсу API; берётся из `usage` в `agent-status.json`, образ onec-agent с учётом токенов, 21.11.2026). Затем карточка дублируется в комментарий issue — `tools/task-board.sh card <issue> --markdown` вставляется в закрывающий комментарий; затем `set <issue> state=closed`.
4. **Раз в неделю** — `tools/task-board.sh scorecard --days 7`: сводка по харнесам и моделям (задачи, ревью и прогоны на задачу, хотфиксы, часы, токены, $). Это основание для выбора исполнителя (критерий «Эффективность» выше); сводку архитектор кладёт в свой отчёт. Тогда же — `tools/update-from-template.sh --check` (раздел «Обновление правил из шаблона»).

## Что положить в промпт запуска

Правило задаёт порядок работы, но не знает условий конкретной задачи. Тот, кто запускает агента, указывает в промпте:

- **Объём правок**, если он шире или уже правила «только `src/`»: документация API, каталоги, тесты.
- **Стенд и тестовые данные**: какая база, разрешено ли создавать собственные технические документы, что делать с очисткой, какие документы только читать.
- **Регрессию для выпуска**: какие тесты репозитория и какую коллекцию API-проверок прогнать и с каким выпуском сравнивать.
- **Принятые решения**, которые нельзя пересматривать, и ограничения (что не ослаблять, какие объекты метаданных запрещено добавлять).
  Запрет на права формулируй точно: «права на данные, RLS и профиль безопасности не менять». Право `Use` роли API на новый шаблон URL HTTP-сервиса — обязательная часть нового метода, без него метод недоступен роли и падает проверка прав; общий запрет «роли не менять» агент выполнить не может (1c-integration-api-bp #106).
  Запреты в промпте — только ограничения владельца и необходимые для безопасности задачи. Настройки **временной копии** (константы и функциональные опции вроде `ИспользоватьДатыЗапретаИзменения`, свои тестовые пользователи БСП без служебных ролей) агенту разрешай менять на время проверки — с записью исходного значения в протокол и возвратом в конце; не запрещай их «на всякий случай». Если сценарий нельзя проверить без такой настройки, а копия временная, — сначала разреши настройку, «не проверено» допустимо только когда её нельзя изменить без нарушения ограничений владельца. Повод: 21.11.2026, 1c-integration-api-bp #149 — архитектор запретил включать даты запрета на копии, и `PERIOD_CLOSED` ушёл в релиз «не проверенным», хотя в #101 его на копии проверяли.
- **Доска задач** живёт на хосте архитектора (`tools/task-board.sh` в основной копии): `claim`/`release` стенда делает архитектор до запуска и после приёмки. Агенту в контейнере доску не поручай — его копия скрипта пишет в доску контейнера, которую никто не видит (#106).
- **Форму сдачи**: PR или `change.patch`, артефакты, протокол.
- **Большую задачу — частями примерно по часу**, с контрольной точкой после каждой: тесты части, коммит и push, `agent-state set <task> question` с отчётом части; архитектор отвечает «продолжай» или замечаниями. Последней строкой промпта и каждого ответа повторяй обязательный последний шаг хода: `agent-state set <task> question|review|error`. Повод — 1c-integration-api-bp #156: два прогона Cursor (≈43 мин, ≈700 тыс. входных токенов) закончились сводкой без статуса и без коммита; этап 2 частями — ни одного обрыва.
- **Регрессию по новой функциональности** — явно: прогон новой папки коллекции API-проверок (Newman) против тестовой базы, итог в протокол. Иначе агент гоняет только старые папки (#156: запросы новой папки шли с двойным префиксом URL и отвечали 404, заметили соседи после релиза).
- **Загрузку релиза на общий стенд — файлом актива**: «загрузи скачанный `<тег>.cfe` (sha256 сверен), не исходники тега» — иначе агент грузит XML тега, и на стенде оказывается не та сборка, что прошла гейт (#156 этап 2).
- **Гейт релиза — обязательный пункт чек-листа приёмки**: «перед `review` — `tools/release-gate.sh --load` на голове PR, итог PASS; `out/release-gate.txt` — в отчёт, `out/release-gate.json` — в `<task-dir>/evidence/`; без отчёта гейта сдача в `review` не принимается» (`headless-agent.mdc` п. 5). Если нужен шаг на демо-базах актуальных версий БП — в промпт `--demo-bases <список>` (включается, когда в Devbox появятся инструменты обновления демо-баз и проект задаст `RELEASE_GATE_DEMO_CMD`; сейчас Фреш проверяет на БП 3.0.210.11 и 3.0.211.21, стенд — 3.0.210.8). Если нужны обычные формы — в промпт `--thick-client-scenarios <файлы>` или `RELEASE_GATE_THICK_CLIENT_SCENARIOS` в `.dev.env` (шаг `thick-client:<файл>`). Архитектор сверяет у шага `thick-client:*`: `status` PASS, `thick_client_verdict` PASS, `thick_client_report_sha256` = sha256 сданного `thick-client-check.json`.
- **Гейт релиза для правки основной конфигурации в проекте «только хранилище»** (`EXTENSION_NAME` пуст, `REPOSITORY_PATH` задан; режим `main-config`): командные строки проверок в промпт больше не пишешь — в промпт идут базовый коммит и перечень файлов задачи. До правок: `tools/release-gate.sh --baseline --base <стартовый коммит>` (база — в состоянии этой версии хранилища; базовая линия `CheckModules`/`CheckConfig` в `out/release-gate-baseline/`). Перед `review`: `tools/release-gate.sh --load --base <коммит> --files '<файл>,<каталог>/*' --patch <task-dir>/change.patch`. После помещения в хранилище: тот же вызов с `--build-cf` — `.cf` базы и его sha256 (без `--load`: база уже в итоговом состоянии). Режимы клиента — `RELEASE_GATE_CHECK_MODES` в `.dev.env` проекта (обычные формы — `-ThickClientOrdinaryApplication -Server -ExternalConnection`). Гейт сравнивает замечания с базовой линией без номеров строк, поэтому сотни замечаний типовой на поддержке не валят приёмку, а новые — валят. Новое замечание, которое ты разобрал и принял (например, следствие смены режима совместимости, а не дефект правки), — строкой в файле `--accepted <файл>` с причиной в комментарии; файл даёшь агенту ты, его путь и sha256 попадают в отчёт (EPRIBOR-3749: 7 строк «ОбщаяКартинка.…: Имя не уникально!» после перехода на 8.3.3). Прогоны проверок, снятые до появления этого режима, принимаются как базовая линия через `--import-baseline <CheckModules /Out> <CheckConfig /Out>` — в отчёте это помечено «импортирована» (ep-trade, EPRIBOR-3749, 22.11.2026).

Регрессию проекта, отметку ограничений стенда и учёт своих тестовых данных правило требует и без промпта (п. 5). Промпт уточняет состав и базу сравнения: то, что выяснится только на приёмке, стоит лишнего цикла.

### Где агент запускает проверки

Тесты, регрессию, параллельные испытания и сборку headless-агент выполняет в своём контейнере dev-workplaces против назначенной ему (обычно временной) тестовой базы: `tools/designer-batch.sh` (CheckModules/CheckConfig с `-Extension`), vrunner, тесты репозитория, коллекция API, `cfe unload`. Каждый лог привязывается к SHA коммита. Требование «тесты только через Woodpecker» (skill `workstation-testing`) относится к рабочей станции владельца и на контейнер агента не распространяется (решение владельца 18.11.2026). Архитектор указывает это в промпте, чтобы агент не останавливался с вопросом.

## Промпт запуска

```
Ты разработчик. Загрузи .cursor/rules/headless-agent.mdc. Задача: openspec/changes/<id>/, Jira <KEY>, task-id <task>.
```

Подстановки: `<id>` — каталог изменения, `<KEY>` — ключ Jira, `<task>` — идентификатор для `agent-state`.

## Команды обёрток в контейнере

- `agent-state get <task>` — прочитать состояние.
- `agent-state set <task> <состояние> [--message-file F] [--pr URL] [--patch PATH] [--artifact PATH]...` — состояния `working`, `question`, `review`, `committed`, `error`.
- Каталог задачи: `$AGENT_TASKS/<task>` (по умолчанию `/home/dev/tasks/<task>`); сюда же идут `change.patch` и `out/`.

## Цикл

1. `working` — разработка по `tasks.md`.
2. `question` — агент остановился с вопросом; ответ приходит продолжением сеанса.
3. `review` — сдан PR или `change.patch` и отчёт; в базу и хранилище агент больше не пишет. До `committed` или `error` задача держит тестовую базу: один контейнер ведёт одну задачу за раз, а ту же базу другой контейнер не получит (блокировка по `INFOBASE_PATH` из `.dev.env`).
4. Приёмка: продолжением сеанса приходит строка `ПРИЁМКА: принято, зафиксируй`; замечания возвращают в `working`.
5. `committed` — помещение в хранилище (комментарий `<id> <KEY>`) или слияние, тег и релиз; сборки cf / cfe / epf в `<task>/out/`. Статус принимается только после приёмки (`agent-reply --accept`), иначе `agent-state` отвечает кодом 4. Если есть и хранилище, и репозиторий, сначала хранилище, затем слияние, тег и релиз; сбой одной половины — `error` с описанием сделанного.
6. `error` — неустранимая ошибка, причина в файле сообщения.

## Сопровождение архитектором

Архитектор (Claude или другой агент) отвечает за результат задачи и за то, сколько он стоит в токенах. Полномочия роли — что архитектор решает сам и что только с владельцем — задаёт ролевая инструкция [SVC-033-I](https://github.com/mikhailchuklay/1commerce-regulations/blob/main/SVC/SVC-033-I-tech-architect.md) в 1commerce-regulations (сессию к ней направляет правило `.cursor/rules/tech-architect.mdc`); разделы этого документа описывают процедуры. Задача — нужное качество за минимум ходов агента и своих.

- **Готовь рабочее дерево полностью.** `git worktree` не наследует неотслеживаемые файлы базового клона: копируй `.dev.env`, `.dsh/agent.env`, `.mcp.json` или `.codex/config.toml`, `AGENTS.local.md`. Без них агент работает без MCP (задачи #41 и хотфикс 1.48.1.1 в 1c-integration-api-bp).
- **QA MCP включён у каждого агента с парой QA.** Контейнер с парой (`onboard-agent.sh --with-qa`) видит `http://qa:8020/mcp`, но маршрут работает, только если: токен пары (`MCP_QA_HTTP_TOKEN` из `/data/compose/.env.qa-agent-<h><N>`) лежит в `~/.secrets/mcp.env` агента как `QA_MCP_TOKEN` и `ONEC_MCP_QA_TOKEN` (вносит владелец, SVC-033-I §4); `TOOL_QA` в `.dev.env` не `off`; харнесу прописан сервер — Cursor: `1c-qa` в `.cursor/mcp.json` (`Authorization: Bearer ${env:QA_MCP_TOKEN}`), Codex: `[mcp_servers.1c-qa]` с `bearer_token_env_var = "QA_MCP_TOKEN"` в `.codex/config.toml`, DSH: `ONEC_MCP_QA_URL=http://qa:8020/mcp` в `.dsh/agent.env` (без `ONEC_MCP_QA=off`). Проверка готовности: `tools/list` с токеном отдаёт инструменты `qa_*`/`ui_*`, без токена — 401. Без этого UI-сценарии и проверка типовых форм остаются «не проверено» (1.49.0.0 в 1c-integration-api-bp: пара QA была, маршрут выключен).
- **Общий стенд — не ниже последнего релиза.** Задачи на одном стенде выпускаются и параллельно: пока идёт твоя, main может уйти на релиз вперёд. Проверять задачу — на временной копии; на общий стенд загружается только ветка, которая содержит свежий `origin/main` и последний релиз, с версией выше выпущенной. Это проверяет `tools/stand-load-guard.sh`: агент запускает его перед каждой загрузкой на общий стенд (`headless-agent.mdc` п. 5), отказ — перебазироваться, а не обходить; `--allow "причина"` — только по слову архитектора, причина в протоколе. Перед `agent-reply`, который ведёт к загрузке, и перед приёмкой сверь то же сам (`git merge-base --is-ancestor origin/main <ветка>`). Хотфикс 1.49.1 после выпуска 1.50.0.0 откатил acc-demo для всех задач.
- **Спецификация до агента проходит `openspec validate <id> --strict`.** Секция `## Why` в proposal, хотя бы один `#### Scenario` у каждого требования и текст требования не длиннее 500 символов (подробности — в сценарии) — иначе при фиксации `openspec archive` падает. `--skip-specs` и `--no-validate` не являются штатным обходом: дельта обязана применяться в `openspec/specs/<capability>/spec.md` (формат и правила — `openspec/specs/README.md`), иначе суть изменения остаётся только в архиве и следующая дельта не находит целевых требований (#98 этап 2, #109 1c-integration-api-bp). Archive новой capability пишет в `## Purpose` заглушку `TBD - created by archiving change …` — в том же PR замени её настоящим абзацем, иначе `validate --specs --strict` падает (#109: три заглушки). Требование «прежнее поведение сохраняется» дополняй в промпте явными случаями снимка «до/после»: пустая ссылка, битая ссылка, пустые строки — иначе снимок на заполненных данных пропускает смену формата (#98: `recipient` при пустом контрагенте стал `null`).
- **Постановку issue клади в промпт текстом.** Токен `gh` в контейнере агента не читает issues (`Resource not accessible by personal access token`, #109 1c-integration-api-bp); ссылка `gh issue view <N>` в промпте агенту бесполезна — вставь тело issue или его суть в файл промпта.
- **Номер версии — при слиянии, а не при старте, через слот слияния.** Номер в промпте — предварительный. Когда ревью закончено и задача готова к гейту, архитектор берёт слот: `tools/task-board.sh version reserve <issue>` (хотфикс — `--patch`, хотфикс к старому выпуску — `--from X.Y.Z.W --patch`). Команда выдаёт следующий номер от последнего тега в `origin`; слот один на репозиторий, поэтому второй архитектор получает отказ с именем держателя и ждёт, а не сливает параллельно. Только после слота агент вписывает номер, сливает `origin/main` в ветку и гоняет гейт. Слот снимается сам, когда тег с этим номером появился в `origin` (или через 3 часа); отменил слияние — `version release <issue>`. Без слота не перенумеровывай и не перегоняй гейт: так 21–22.11 одна задача трижды меняла номер (ретро #169). Хотфикс к выпуску, после которого уже вышел следующий, — PATCH от текущего main (1.50.1.0, а не 1.49.1.0).
- **После релиза — OpenSpec-изменение в архив.** Шаг готовности задачи, а не хвост: `openspec archive <id> --yes` (дельты переносятся в `openspec/specs/`, изменение — в `openspec/changes/archive/`) отдельным PR от свежего `origin/main`, слитым до закрытия issue. Делает агент при фиксации (`headless-agent.mdc` п. 7); не сделал — архитектор сам, сразу после релиза. Без `--skip-specs` и `--no-validate`: archive применяет дельты, только если `openspec/specs/` лежат в формате `<capability>/spec.md` с требованиями и сценариями (`openspec/specs/README.md`), а имя capability в дельте совпадает с папкой. Проект с плоскими `specs/*.md` сначала переводит их в этот формат (#109 1c-integration-api-bp: с `--skip-specs` суть дельт переносили вручную и теряли — договор счёта из #98 остался только в архиве).
- **«Внесу после задачи» — сразу в карточку.** Обещанная доработка (своя, агента или side-сессии) в тот же ход становится issue или предложением сессии (карточкой) со ссылкой из отчёта; строка «сделаю потом» в отчёте без issue не считается.
- **После релиза — общий стенд на последний релиз.** Шаг готовности задачи: архитектор, выпустивший релиз, загружает релизную сборку на общий стенд проекта (тем же двухшаговым путём, после `tools/stand-load-guard.sh` на теге), проверяет версию и новые признаки (`GET /info` или аналог проекта) и пишет итог в отчёт и в комментарий к задаче. Цель загрузки задаёт `VRUNNER_IBCONNECTION`, а не `INFOBASE_PATH`: в сеансе `agent-run` она уже указывает на рабочую базу задачи (обычно временную копию). Поэтому подмена `.dev.env` или `source` другого файла цель не меняет: перед загрузкой на стенд выставь `VRUNNER_IBCONNECTION`/`VRUNNER_DBUSER`/`VRUNNER_DBPWD` стенда явно; при расхождении `stand-load-guard.sh` откажет. Загрузка не считается выполненной, пока `GET /info` стенда не показал новую версию. Если версия прежняя, первым делом проверь цель подключения, а не кэш публикации (20.11.2026, #100 1c-integration-api-bp: релиз дважды лёг в копию, агент списал прежнюю версию стенда на кэш). Если стенд держит чужая задача в `working`/`review` — договориться с её архитектором и загрузить сразу после неё. Архитекторам задач на том же стенде — одна строка: что изменилось в API.
- **Уборка — шаг готовности задачи, следишь ты.** Задача не закрывается (`committed` агента, закрытие issue), пока за ней остаётся мусор. Проверяешь сам при приёмке и после релиза, а не веришь отчёту:
  - **Временные копии баз** этой задачи удалены: публикации сняты, `infobase_drop`, `tools/task-board.sh release <копия> --holder <сессия> --drop`; на доске нет `--temp`-записей задачи. Временную копию (`temp=true`) удаляешь сам, без владельца; проверка — базы нет в `infobase_list`. Копия наследует пользователей ИБ исходной базы. Если `infobase_drop` отвечает `412` («rac не пустил… задайте ib_user»), удаляй с `clear_ib_users=true`: сначала `dry_run` — в плане должны быть твоя копия, `temp` и 0 сеансов. Подтверждение владельца нужно только для копии, созданной без `temp` (до 20.11.2026 или по ошибке): тогда номер задания и подтверждения — в отчёт и в напоминание владельцу в том же ходе. Копию, которую передаёшь следующей задаче, перезаписываешь на доске на её архитектора — так она не теряется.
  - **Контейнер агента**: агент удалил явный мусор задачи — рабочее дерево `~/work/<task>` после слияния, временные каталоги сборки (`~/cfe-build-*`), выгрузки конфигурации и баз (`.dt`, `.cf`, XML-выгрузки типовой) в `~/tasks/<task>`. Остаются `report*.md`, `evidence/`, `out/` (релизная сборка), журналы прогонов. Проверка — `du -sh ~/tasks/<task> ~/work/<task>` в контейнере; больше сотен мегабайт без причины в отчёте — возврат агенту или уборка сам. Рабочие деревья убирает `tools/agent-workspace-cleanup.sh [--apply] <контейнер>` (по умолчанию — план): он удаляет только git worktree в `~/work`, ветка которых влита в `origin/main` или запушена, пропускает деревья активных задач (`agent-state` working/question/review), каталоги с живыми процессами, клоны и всё вне `~/work`, а незакоммиченное сохраняет патчем в `~/tasks/<каталог>/`. Каталоги закрытых задач, оставшиеся от прошлых сессий, убираешь тем же скриптом сам: **уборка мусора — зона архитектора, владельцу на согласование не выносится** (решение владельца 19.11.2026). Блок режима auto на ad-hoc `rm -rf` — повод взять скрипт, а не спрашивать владельца. Подтверждение владельца остаётся только там, где его требует сама система (удаление базы в Devbox).
  - **Тестовые данные на стенде** — по списку GUID агента помечены на удаление (`headless-agent.mdc` п. 5), сверено чтением.
  - **Сторонние эталонные базы** (пустая БП нужной версии для сверки и т. п.) — по тем же правилам, что временные копии.
  Повод: 18.11.2026 общий том `/data` контейнеров заполнился на 99 % — выгрузки БП по 4,9 ГБ из давно выпущенных задач лежали в контейнерах, временная IB 79 жила после релиза, потому что подтверждение удаления ждали без напоминания.
- **Внешнее действие подтверждается ответом получателя, а не своим статусом.** Отправка в банк, ЭДО, письмо, загрузка в чужую систему считается выполненной только по ответу или квитанции получателя (статус банка «принят»/«исполнен», квитанция ЭДО, идентификатор во внешней системе). Локальный статус («Отправлен в банк», «Отправлено») — только то, что вызов ушёл. В промпт агента пиши, какой ответ получателя считается доказательством и сколько его ждать; без него агент ставит `question`, а не продолжает сценарий и не сообщает «отправлено». Повод: #76 1c-integration-api-bp — платёжка на 1 ₽ «отправлена» по статусу копии, а в банке её не оказалось.
- **Сначала проверь исполнителя.** До старта задачи или side-сессии посмотри, не ведёт ли её уже агент: `agent-state get <task>` в контейнерах и реестр блокировок. В брифе любой сессии пиши строку «исполнитель: <контейнер>/<task> | нет». Без этого две сессии делают одну правку дважды (хотфикс 1.48.1.1: бриф «восстанови функцию» ушёл в сессию, пока задача уже шла на dsh1).
- **Следи сам, а не жди статуса.** После `agent-run` поставь фоновое ожидание `tools/agent-monitor.sh --exit-on-idle <контейнер> <task> <N> <рабочее-дерево>` фоновой командой Bash (`run_in_background`), а не инструментом Monitor: у Monitor лимит 30 минут, и долгую задачу приходится перезапускать (15 перезапусков в #41 1c-integration-api-bp). Фоновая команда будит архитектора, когда скрипт выходит: код 0 — состояние `review`/`question`/`error`/`committed`, код 3 — первый простой (посмотри на агента и запусти монитор снова). Скрипт бери из `tools/` своей рабочей копии, а не копией во временной папке: временная копия отстаёт от шаблона. Сигналы: смена состояния или простой дольше N минут (файлы рабочего дерева и `~/tasks/<task>` не менялись, нет процессов `1cv8`/`vrunner`). Рост `run-N.log` — не признак: Cursor с `-p --output-format json` пишет лог только в конце прогона (ложный простой в задаче #43 1c-integration-api-bp). Смотри хвост JSONL (последние вызовы и мысли), а не весь лог: полный лог — сотни килобайт контекста.
- **Вмешивайся сразу.** Агент ищет то, чего нет в среде, гоняет одну и ту же проверку, ждёт модальное окно, ушёл за объём задачи — ответь или исправь среду, не дожидаясь `review`. Правку, которая перезапускает идущий прогон (образ, окружение контейнера), применяй после его завершения.
- **Закрывай причину, а не случай.** Каждое трение (недоступный инструмент, неясное правило, ложный «PASS») — правка окружения, инструмента или промпта сразу, правки шаблона по итогам задачи — PR, который архитектор сам проверяет и сливает (ниже, «PR задач — твои»), правки общего регламента 1commerce-regulations — предложением владельцу как менеджеру процесса: проблема → доказательство из прогона → правка → экономия.
- **Ретро — шаг приёмки, без команды владельца.** При приёмке каждой задачи (до слияния) и при её закрытии просмотри протокол: вопросы агента, круги ревью, упавшие прогоны, отказы инструментов, обходы. Каждое трение — правка сразу (промпт, инструмент, шаблон — PR, который сливаешь сам; devbox/инфраструктура — issue в их репозитории); в отчёт задачи — строка «Ретро: трение → правка/issue» или «Ретро: трений нет» и строка «Исполнитель: <харнес>/<модель> — подошёл / не подошёл: причина (круги ревью, ошибки, время)»; «не подошёл» запускает переоценку (раздел «Переоценка харнесов и моделей»). Владелец не должен спрашивать, что улучшить (19.11.2026).
- **Подтверждения Devbox живут около двух часов.** Временные копии с `temp=true` подтверждения не требуют. Остальные подтверждаемые задания ставь, когда владелец на связи, номер подтверждения — в тот же ход. Истекло (`approval истёк (TTL)`) — перезапроси сам и сообщи новый номер, а не повторяй старый (19.11.2026: 804 и 808 истекли до клика).
- **После перезапуска приложения фоновые мониторы умирают.** Первым ходом после перезапуска проверь `agent-state` своих задач и перезапусти `tools/agent-monitor.sh`; «working» без монитора — слепая зона (19.11.2026, #98 и #101).
- **Сценарий фикстуры — проверяемым свойством, а не словом.** Пиши в промпте, что именно должно совпасть или пересечься («две выписки с общими операциями», «один и тот же документ в обеих»), а не общее слово («пересекающиеся периоды»): агент выполнит букву. 20.11.2026, #96 1c-integration-api-bp: «пересекающиеся периоды» дали фикстуру без общих операций, проверка не ловила дубли (R4).
- **Арифметика дат 1С — в секундах.** `Дата ± Число` сдвигает на секунды, а не на дни (`ТекущаяДатаСеанса() - 3600` — час назад). Правку такого выражения принимай только с воспроизведением на базе. 20.11.2026, #96: агент «исправил» верное `- 3600` на `- 1/24`, окно стало меньше секунды.
- **Отклонить замечание валидатора как ложное — только с воспроизведением.** Покажи вход, на котором замечание не срабатывает; без этого замечание — дефект. 19.11.2026, #98: «параметр не установлен» отклонили как ложное, а это был 500 на нулевом UUID.
- **Схема MCP в клиенте может отстать от сервера.** После выкатки нового параметра у уже запущенной сессии клиент шлёт его строкой (422 на массиве), Reconnect помогает не всегда. Проверь `tools/list` сервера напрямую; если там поле есть — вызови `tools/call` по HTTP с тем же токеном, а не жди перезапуска (19.11.2026, devbox `inet`).
- **Лимит или баланс харнеса — блокер исполнителя, а не задачи.** `QUOTA`/`Insufficient Balance`/`LIMIT` в `run-N.log` — сразу сообщение владельцу одной строкой (пополнение — его действие) и выбор другого свободного контейнера; задача держит стенд и ждёт.
- **Улучшай по своей инициативе, не спрашивая.** Если считаешь улучшение верным (инструмент, обёртка, скрипт, правило или процедура шаблона, промпт), делай его сам без поручения и без согласования с владельцем: правка, PR, ревью, слияние, `/updaterules`. Не предлагай владельцу карточкой то, что вправе сделать сам. Объёмную правку или правку вне текущей задачи веди в отдельной сессии со своей веткой и PR, чтобы не задерживать задачу. Решение, которого нет в перечнях SVC-033-I, принимаешь сам и записываешь в отчёт с причиной.
- **Приёмка по существу.** Ты владелец кода: ревью PR (корректность, транзакции и блокировки, контракт, тесты) и сверка доказательств с SHA; «зелёный» без командной строки и лога не принимается.
  - **Отчёт гейта сверяется механически, проверки не перезапускаются.** `release-gate.json` агента: `sha_head` = голова PR (`gh pr view --json headRefOid`), `result` = PASS и все шаги PASS (ни одного `SKIPPED`), `loaded_by_gate` = true либо в отчёте объяснено, чем загружена база, `cfe_sha256` = файл релиза — после публикации скачай актив релиза (`gh release download <тег> -p '*.cfe'`) и сверь `sha256sum`. Актив загружай под латинским именем `<тег>.cfe` (копия сборки гейта, тот же sha256): кириллическое имя `<EXTENSION_NAME>-<версия>.cfe` GitHub превращает в нечитаемое вида `1._.API_.-1.55.0.0.cfe` (19.11.2026, 1.55.0.0 1c-integration-api-bp). В релиз идёт та самая сборка гейта (`out/<EXTENSION_NAME>-<версия>.cfe`) без пересборки; новый коммит после приёмки — новый прогон гейта. Любое расхождение — возврат агенту без собственных прогонов: из 11 релизов 17–18.11.2026 три потребовали хотфикса, потому что агент сам собирал командные строки проверок и сообщал PASS (1.48.1.0 — `/CheckModules` без `-Extension`, 1.49.0.0 — форма не проверена, 1.51.1.0 — блокер анализатора).
    Режим `main-config` (`"mode": "main-config"`): вместо версии и `cfe_sha256` сверяешь `base_sha` = стартовый коммит из промпта, `files_scope` = объекты задачи, `patch_sha256` = `sha256sum` сданного `change.patch`, `accepted_findings` — только твой файл (sha256 сверь), `baseline.base_sha` = `base_sha` и `baseline.source` (`gate` — снята гейтом, `imported` — прежние логи, тогда сверь пути и `imported_sha256`). После фиксации — второй отчёт с `--build-cf`: `cf_sha256` = артефакт `committed`.
  - **Матрица приёмки** — в комментарии ревью PR: каждый сценарий дельта-спецификации → доказательство (команда, лог, SHA) или «не проверено» с причиной. Сценарий без строки матрицы — не принят.
  - **Типовое сначала.** Решение, которое опирается на типовой механизм БП/БСП (проведение, регистр, обработчик, общий модуль), ссылается на модуль:строку выгрузки типовой той версии, на которой проверялось. Без ссылки — замечание в ревью, а не приёмка. Раздел «Валидаторы» отчёта `agent-state` сверяй с протоколом построчно: блокер валидатора, отложенный в протоколе «до решения владельца» или «в следующий патч», — не приёмка, а замечание (1.49.0.0: блокер `syntaxcheck` был только в протоколе, отчёт называл валидатор недоступным). «Не проверено» по инструменту, который можно починить в среде, тоже не принимается: сначала чинишь среду, потом прогон.
- **PR задач — твои: проверяешь и вливаешь сам.** Все PR, которые появились при выполнении задач разработки, идущих через архитектора, — его ответственность, и владельца он не ждёт. Сюда входят PR агентов, side-сессий, правок правил и шаблона по итогам задачи. Порядок такой:
  1. Ревью diff по существу и сверка доказательств: командные строки, логи, SHA.
  2. Чистка мусора (байткод, протоколы агента в корне).
  3. Комментарий ревью в PR.
  4. Слияние. В репозитории с ruleset «review для внешних PR» — через исключение владельца (`gh pr merge --admin`).
  5. Если менялся шаблон — строка в `CHANGELOG-TEMPLATE.md` в том же PR; проекты-потребители забирают правила по регламенту «Обновление правил из шаблона» (подписчики `consumers.json` — автоматически), свой проект архитектор синхронизирует перед следующим `agent-run`.
  PR людей и сессий вне задач архитектора — только по слову владельца. Тег и релиз — по регламенту релиза задачи.
- **Закрытие задачи — тоже твоё.** После релиза архитектор сам закрывает issue задачи с коротким комментарием: релиз, PR, что осталось непроверенным, карточка задачи с доски (`tools/task-board.sh card <issue> --markdown`). Непроверенное идёт в описание релиза, а реальная доработка — в новую задачу; issue «на решение владельца» открытым не оставляется. За владельцем остаются только действия из SVC-033-I, требующие согласия (Фреш и каталог, рабочие базы, секреты, массовые записи на общем стенде, утверждение общего регламента).

## Инструменты базы и хранилища (vanessa-runner)

В Linux-контейнере агента есть PowerShell 7 (`pwsh`, образы `onec-agent-cursor` и `onec-desktop` с 09.11.2026): инструменты правки метаданных скилла `1c-metadata-manage` (`cfe-*`, `cf-*`, `form-*`, `meta-*`, `skd-*`, `role-*`, `mxl-*`) запускаются как `pwsh -NoLogo -NonInteractive -File <скрипт.ps1> …` с теми же параметрами, что на Windows; результаты прогона — `docs/linux-compat.md`. Не работают на Linux только скрипты, которые запускают `1cv8.exe` по Windows-путям: `db-*`, `epf-build`, `epf-dump`, `stub-db-create` (`1c-metadata-manage`) и `repo-ops.ps1` (`1c-repository-manage`). Их заменяет vanessa-runner 3.x: MCP-сервер `vrunner` в `.cursor/mcp.json` (в шаблоне выключен, в контейнере включается: `"disabled": false`) и та же утилита в оболочке, `xvfb-run -a vrunner …` (платформе нужен виртуальный экран).

Параметры подключения агент не задаёт сам: `agent-run` выставляет их из `.dev.env` проекта и файлов `~/.secrets` контейнера. Уже заданные переменные не перезаписываются.

| Переменная vrunner | Откуда |
|---|---|
| `VRUNNER_IBCONNECTION` | `INFOBASE_PATH`: при `INFOBASE_KIND=server` `сервер:порт/база` → `/Sсервер:порт\база`, иначе `/F<путь>`; значение, начинающееся с `/F` или `/S`, берётся как есть |
| `VRUNNER_V8VERSION` | имя каталога `PLATFORM_PATH` (`/opt/1cv8/x86_64/8.5.1.1343` → `8.5.1.1343`) |
| `VRUNNER_DBUSER` / `VRUNNER_DBPWD` | `IB_USER` / `~/.secrets/ib-password` |
| `VRUNNER_STORAGE_NAME` / `_USER` / `_PWD` | `REPOSITORY_PATH` / `REPOSITORY_USER` / `~/.secrets/storage-password` |
| `VRUNNER_EXTENSION_NAME` | `EXTENSION_NAME` |

Пароли в `.dev.env` контейнера не пишутся: `IB_PASSWORD` и `REPOSITORY_PASSWORD` оставить пустыми.

### Какой инструмент для какой операции

По прогону ep-trade (УТ 10.3, «только хранилище», EPRIBOR-3749, 22.11.2026):

| Операция | Инструмент | Почему не vrunner |
|---|---|---|
| Хранилище: захват, обновление, помещение, отпуск | `vrunner` в оболочке (`xvfb-run -a vrunner …`) | MCP `repo_lock` не передал пользователя базы, захват прошёл только из оболочки |
| Выгрузка конфигурации, `infobase update`, загрузка расширения | `vrunner` (раздел ниже) | — |
| Загрузка основной конфигурации в базу, подключённую к хранилищу | `tools/designer-batch.sh --load --repository -- /LoadConfigFromFiles <src> -listFile <список>` — только захваченные объекты; гейт `release-gate.sh --load` в режиме `main-config` собирает список сам | полный `vrunner cf load` платформа отклоняет («Загрузка невозможна: текущая конфигурация помещена в хранилище»), а `cf load` не передаёт параметры хранилища |
| Кластер и сеансы: список, завершение своих | `rac` или Devbox MCP (`infobase_sessions`, `infobase_session_terminate`) | `vrunner cluster session list` и MCP `session_list` падают в irac («Значение не является значением объектного типа»), без `VRUNNER_RAS` идут на `localhost:1545`; `rac` работает |
| Пакетные проверки Конфигуратора (`/CheckModules`, `/CheckConfig`, `/CheckCanApplyConfigurationExtensions`) | `tools/release-gate.sh` (зафиксированные командные строки через `designer-batch.sh`) | — |
| Режим Предприятия: обычные формы, печать, отчёты в толстом клиенте | навык `1c-thick-client-test`, обёртка `tools/thick-client-check.sh` | `vrunner run` не отключает логику начала работы БСП и зависает на модальных окнах (vanessa-runner#378) |
| Управляемые формы | QA MCP `1c-qa` (`ui-testing-tools.mdc`) | — |

### Загрузка расширения только через Конфигуратор

Для vanessa-runner 3.0.2 загрузка из XML или `.cfe` выполняется в два шага. Запускать в окружении агента, где уже заданы параметры `VRUNNER_*`. `EXTENSION_NAME` и `SOURCE` ниже задаются явно из параметров проекта и выбранного источника:

```bash
: "${EXTENSION_NAME:?Нужно имя расширения}"
: "${SOURCE:?Нужен каталог исходников или файл .cfe}"
xvfb-run -a vrunner cfe load --no-update-db --extension-name "$EXTENSION_NAME" "$SOURCE" &&
  xvfb-run -a vrunner infobase update --target "$EXTENSION_NAME"
```

Первый шаг только загружает конфигурацию расширения. Второй применяет её к БД, только если первый завершился успешно. Не передавать второму шагу `--src`, пустой `--target` или `--ibcmd`. Это не запуск обработчиков обновления БСП: если они нужны, их выполнение остаётся отдельной операцией.

Обычный `cfe load` после обновления БД безусловно запускает Предприятие для изменения свойств расширения — отсутствие флагов свойств не предотвращает этот запуск. В двухшаговом варианте этот участок пропускается. Активность, безопасный режим и защита от опасных действий этим способом **не устанавливаются**; для нового расширения проверять их отдельно. Не подменять проверку свойств утверждением, что переданные при загрузке `--active` или `--safe-mode` сработали: с `--no-update-db` они не применяются.

MCP-эквивалент: `cfe_load` с параметром пропуска обновления БД и явным именем расширения → успешный `task_result` → `infobase_update` с `target`, равным имени расширения. Имена и типы аргументов брать из текущей схемы инструментов, а не переносить написание CLI-флагов наугад; если нужных аргументов нет — использовать CLI выше.

Ошибка обновления (например, пересечение идентификаторов с OneMCP) означает, что расширение не применено к БД, даже если загрузка исходников прошла. Остановиться и сохранить лог, без повторов и без запуска тонкого клиента.

Ограничения, проверенные на БП 3.0 / 8.5.1:

- Операции Конфигуратора (загрузка и выгрузка, обновление БД, хранилище, сборка) идут без окон только на виртуальном экране (`xvfb-run -a`, `tools/designer-batch.sh`) и с `/DisableStartupDialogs`. Без этого окно ошибки открывается на экране сеанса и процесс ждёт нажатия OK. Если контейнер — рабочее место человека, окно появляется у него (08.11.2026: выгрузка по `-listFile` в пустой каталог, «объект метаданных не существует»).
- Операции Предприятия (список и проверка расширений, тесты YAxUnit/Vanessa, свойства расширения после загрузки) могут зависнуть на модальном окне БСП: «Предупреждение безопасности» при первом входе пользователя с правом открывать внешние обработки, окна первого запуска после изменения конфигурации. vanessa-runner формирует `/C` сам и не передаёт `ОтключитьЛогикуНачалаРаботыСистемы` (issue vanessa-opensource/vanessa-runner#378). Первый вход пользователя агента делает человек и закрывает окна.
- MCP-инструменты `cfe_*` (vrunner 3.0.2) не берут имя расширения из `VRUNNER_EXTENSION_NAME` и без явного `extension_name` работают с основной конфигурацией: `cfe_unload` выгрузил всю конфигурацию БП вместо расширения. Утилита в оболочке переменную учитывает. Правило агента требует передавать имя явно.
- Прерванный запуск оставляет сеанс в кластере, который блокирует обновление БД: после тайм-аута завершать свои сеансы.

### Пакетный Конфигуратор: `tools/designer-batch.sh`

Инвариант для любой среды: процессы `1cv8` / `1cv8c`, запущенные агентом, не используют дисплей человека и не ждут диалог.

| Среда | Как выполняется |
|---|---|
| Windows | `Start-Process -WindowStyle Hidden` + флаги (рецепт `designer-batch-checks.mdc`) |
| Linux с X-сеансом | только `xvfb-run -a` или свой `Xvfb`; `DISPLAY` сеанса не используется |
| Linux без X | `ibcmd` или `vrunner` под `xvfb-run -a`; без виртуального экрана Конфигуратор не запускается |

Флаги `/DisableStartupDialogs /DisableStartupMessages /Out /DumpResult` и тайм-аут обязательны всегда. Предпочтение: `ibcmd` → `vrunner` → `tools/designer-batch.sh`. Прямой вызов `1cv8` без обёртки запрещён.

```bash
tools/designer-batch.sh -- /CheckModules -ThinClient -Server -ExternalConnection -Extension "$EXTENSION_NAME"
tools/designer-batch.sh --timeout 1800 -- /DumpConfigToFiles "$DUMP_DIR"
```

Обёртка берёт платформу, базу и пользователя из `.dev.env` (запасной вариант — `VRUNNER_*`), запускает Конфигуратор на своём виртуальном экране (`xvfb-run -a`, иначе свой `Xvfb`; первый номер — `DESIGNER_XVFB_FIRST`, по умолчанию 99), снимает `WAYLAND_DISPLAY`, по тайм-ауту (`--timeout`, `DESIGNER_TIMEOUT`, по умолчанию 600 с) гасит только свою группу процессов. Вердикт — по трём сигналам: код возврата, `/DumpResult`, текст `/Out`. Коды: 0 — успех, 1 — не прошло или тайм-аут, 2 — запуск отклонён, 3 — нет виртуального экрана. Отклоняются: больше одной пакетной команды, ключи подключения и вывода в аргументах, запрещённые операции (`/EraseData`, `-AllExtensions`, `/DeleteCfg` без имени, `-disableSupport`, `/IBCheckAndRepair`), частичная выгрузка без полной в том же каталоге. `--dry-run` показывает команду со скрытым паролем, `--self-test` проверяет разбор лога.

## Обычные формы: навык `1c-thick-client-test`

Формат сценария, контракт отчёта и ограничения — в `.cursor/skills/1c-thick-client-test/`. Точка входа — `tools/thick-client-check.sh`.

QA MCP и тест-клиент ведут управляемые формы. Обычное приложение, обычные формы, клиентский код `#Если Клиент` и `#Если ТолстыйКлиентОбычноеПриложение`, печать и формирование отчётов проверяет толстый клиент `1cv8` через `tools/thick-client-check.sh`. Управляемые формы по-прежнему идут через `1c-qa`.

Обёртка поднимает свой `Xvfb` (`-nolisten tcp`, номер с 120, унаследованный `DISPLAY` не используется), запускает `ENTERPRISE /RunModeOrdinaryApplication` с подключением из `.dev.env` (`INFOBASE_KIND`, `INFOBASE_PATH`, `PLATFORM_PATH`, `IB_USER`, `IB_PASSWORD`, запасной путь — `VRUNNER_*`), флагами `/DisableStartupMessages /Out` и общим `--timeout` (по умолчанию 900 с). `/DisableStartupDialogs` не передаётся: у диалога защиты от опасных действий кнопка по умолчанию — «Нет», и ключ молча запрещает `/Execute`. Такие окна закрывает наблюдатель. По тайм-ауту снимаются только своя группа процессов и свой Xvfb. На Windows скрипт отказывает: нужен Linux. Сборка `.epf` — `tools/designer-batch.sh /LoadExternalDataProcessorOrReportFromFiles` той же платформой и в ту же базу, что и прогон (`--platform`, `--infobase`, `--ib-user`; пустой `--ib-user` — без `/N`). Кэш — sha256 исходников, сборка платформы и версия формата XML. `Form.bin` обычной формы собирает `host.py` (контейнер без индекса кода); `v8unpack` для этого не нужен.

`/Execute` открывает обычную форму. В `ПриОткрытии` она создаёт объект обработки и подключает обработчик ожидания. Печать, отчёты, журнал и запись `.mxl`/`.pdf`/`.txt` выполняет модуль объекта. Снимок `open_form` — обмен маркерами в каталоге прогона; форму после снимка закрывает исполнитель.

Стартовые модальные окна смотрит `xdotool search --pid` своего процесса: снимок, затем закрытие только по белому списку заголовков (в скрипте; дополняется `--dismiss-title «Текст|действие»`, действие `click-left`, `click-right`, `return` или `close`). Неизвестное модальное окно — снимок, ошибка, процесс снят. Enter и Escape без опознанного заголовка не нажимаются.

```bash
tools/thick-client-check.sh scenario --params .cursor/skills/1c-thick-client-test/scripts/example-scenario.json
tools/thick-client-check.sh --infobase onec-dev-server:5541/другая-база --platform 8.3.14.1779 --ib-user '' scenario --params путь/к/сценарию.json
tools/thick-client-check.sh snapshot --metadata Документ.РеализацияТоваровУслуг --number 00-000001
tools/thick-client-check.sh --dry-run scenario --params путь/к/сценарию.json
tools/thick-client-check.sh --self-test
```

Сценарий — JSON, массив `steps`. Обработка читает путь из `/C` (`ПараметрЗапуска`) и идёт по шагам в клиенте толстого обычного приложения. Исключение шага пишется как `ПодробноеПредставлениеОшибки`, прогон продолжается. В конце — `ВыгрузитьЖурналРегистрации` (ошибки и предупреждения с даты начала) и `ЗавершитьРаботуСистемы(Ложь)`.

| action | Что делает |
|---|---|
| `print` | Документ или справочник по `metadata`, `number` и при необходимости `date` / `date_from`+`date_to`. Макет — `layout` (ключ, синоним или единственный префикс). `invoice: true` берёт подчинённый `СчетФактураВыданный` через `УчетНДС.НайтиПодчиненныйСчетФактуру`. Внешняя печатная форма, если она есть в дереве макетов, вызывается штатно и возвращает табличный документ; иначе — `Печать` объекта и таблица из открытой формы печати. Если путь в конфигурации другой, шаг задаёт `module` и `method` (идентификаторы, не произвольный текст). Пишет `.mxl`, `.txt` и, если платформа записала, `.pdf`. |
| `report` | `Отчеты[Имя].Создать()`, период `date_from`/`date_to`, необязательный объект `settings`. `variant` для универсального отчёта без СКД — ошибка шага. Пишет `.mxl`, `.txt`, `.pdf`. |
| `open_form` | `kind`: `object` (ссылка), `list`, `report` (`generate: true` — сформировать), `main` (весь экран). Оболочка ждёт маркер и пишет `.png`, затем форма закрывается. |
| `wait` | `seconds` — пауза обработчиком ожидания. |

`expect_text` — массив строк, которые должны найтись в `.txt` (номер, контрагент, «Итого»). Нет строки, пустой табличный документ или нет обещанного файла — шаг FAIL. Неудача PDF сама по себе шаг не валит: в отчёте остаётся `pdf_error`, доказательство — `.mxl` и `.txt`.

Отчёт прогона: `out/thick-client-check.json` и `out/thick-client-check.txt`. В нём командная строка со скрытым паролем, сборка платформы, база, пользователь, время, по каждому шагу статус, длительность, ошибка и файлы с размером и sha256, снимки закрытых стартовых окон, хвост `/Out` и хвост журнала регистрации, итог PASS/FAIL. Коды: 0 — все шаги PASS, 1 — FAIL или тайм-аут, 2 — отказ в запуске, 3 — нет Xvfb.

Архитектору как доказательство сдаются эти два отчёта, файлы шагов (`.mxl`, `.txt`, `.pdf`, `.png`) и сверка sha256 из отчёта с файлами. Пересказ без файлов доказательством не является. Каталог `out/` в git не входит; в задачу копируется то, что просил сценарий.

Ограничения: только Linux; обычные формы и толстый клиент, не тест-клиент и не тонкий; сценарий не проводит и не записывает документы (запись делает сама печать или формирование, если так устроена конфигурация); модальное окно вне белого списка останавливает прогон; явный `module`/`method` — только путь из идентификаторов; вариант СКД в `report` не подставляется.

## Применение патча на стороне архитектора

Патч делается как `git add -A && git diff --cached --binary > change.patch`, поэтому содержит новые файлы и бинарные изменения. Применять к «было» (чистая выгрузка или основная ветка):

```
git apply --index --binary change.patch
```

`--index` переносит изменения и в индекс (новые файлы попадут в коммит). Бинарные блоки разбираются из патча, сделанного с `--binary`. Проверка без применения: `git apply --check change.patch`.

## Файлы

`tools/agent-workspace-cleanup.sh` — уборка рабочих деревьев агентов в контейнере: план по умолчанию, `--apply` — удалить, `--keep <каталог>` — не трогать. Удаляет только влитые или запушенные git worktree в `~/work` вне активных задач; незакоммиченное — патчем в `~/tasks/<каталог>/`; печатает `du -sh ~/work` до и после. Те же `AGENT_SSH_HOST`, `AGENT_CONTAINER_PREFIX`, `AGENT_EXEC_USER`. Разреши его в `permissions.allow` проекта (`Bash(tools/agent-workspace-cleanup.sh:*)`), чтобы режим auto не останавливал уборку.

`tools/agent-monitor.sh` — фоновое ожидание архитектора по задаче агента: печатает смену состояния и однократное предупреждение о простое, завершается на `review`/`question`/`error`/`committed`, переживает обрыв ssh. Только чтение. ssh-алиас и префикс контейнера задаются `AGENT_SSH_HOST`, `AGENT_CONTAINER_PREFIX`; `--once` — один замер.

`tools/agent-monitor.sh --exit-on-idle` — выход с кодом 3 при первом простое; так фоновая команда Bash будит архитектора и при зависшем агенте.

`tools/release-gate.sh` — гейт релиза агента перед `review`: фиксированные командные строки проверок, отчёт `out/release-gate.json` и `out/release-gate.txt` (SHA HEAD, sha256 сборки, команда, код возврата и хвост лога каждого шага, итог PASS/FAIL), логи в `out/release-gate/`. Коды: 0 — PASS, 1 — FAIL, 2 — ошибка запуска. Два режима: `extension` (правка расширения; `-Extension`, `/CheckCanApplyConfigurationExtensions`, версия и тег, `.cfe`) и `main-config` (правка основной конфигурации в проекте «только хранилище»: чистое дерево, разница только в файлах задачи, `git apply --check` патча на базовом коммите, `check-bsl-calls` против базы, `CheckModules` и `CheckConfig` против базовой линии `--baseline`, после фиксации `--build-cf` — `.cf` и sha256). Режим выбирается по `.dev.env` или ключом `--mode`. Необязательный шаг `thick-client:<файл>` (`--thick-client-scenarios` или `RELEASE_GATE_THICK_CLIENT_SCENARIOS`, оба режима, после сборки и `demo:*`) гоняет `tools/thick-client-check.sh`: в записи шага путь и sha256 сценария и отчёта, `thick_client_verdict`, `wrapper_rc`, `reason`; в корне отчёта — `thick_client_scenarios`. В `.txt` под строкой шага — путь к отчёту, verdict и sha256.

`tools/task-board.sh` — доска задач проекта (очередь, стенды и копии, карточки, недельная сводка); файл `<основная копия>/.task-board/board.json` вне git, запись под `flock`.

`.gitattributes` приводит переносы строк к виду платформы (`*.bsl`, `*.xml` — CRLF) и скрывает `ConfigDumpInfo.xml` из diff, чтобы разница на приёмку содержала только значимые правки.
