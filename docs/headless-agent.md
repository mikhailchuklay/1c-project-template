# Headless-агент разработчика (Cursor CLI, Codex CLI)

Правило `.cursor/rules/headless-agent.mdc` описывает, как агент без интерфейса ведёт одно OpenSpec-изменение в контейнере разработки. Агента запускает человек или архитектор (Claude, другой агент) по ssh; общение идёт через файл статуса. Исполнителя выбирает `AGENT_HARNESS` контейнера: `cursor` (Cursor CLI, MCP из `.cursor/mcp.json`), `codex` (Codex CLI, MCP из `.codex/config.toml`) или `dsh` (DeepSeek Harness со слоем 1С, MCP из `.dsh/agent.env`; рабочее дерево задачи этот файл не наследует — копируй `.dsh/agent.env` и `.mcp.json` из базового клона, иначе бандл ищет серверы на `127.0.0.1:800N` и отвечает `MCP_LOCAL_NOT_RUNNING`). Обёртки `agent-run`, `agent-state`, `agent-reply` одинаковы для всех.

## Выбор исполнителя — зона архитектора

Какому агенту и в какой контейнер поручить задачу, решает архитектор сам, без согласования с владельцем. Владелец не выбирает исполнителя и не подтверждает выбор; он только сообщает ограничения (например, у харнеса закончились лимиты), и архитектор их учитывает до отмены.

Критерии, по порядку:

1. **Доступность.** Контейнер свободен (`agent-state` его задач не в `working`/`question`/`review`), у харнеса есть лимиты, MCP 1С и локальные файлы рабочей копии на месте.
2. **Очередь и стенд.** Не нарушать согласованную очередь работ и блокировку тестовой базы (`agent-run` откажет при занятой `INFOBASE_PATH`). Как развести задачи по стенду — см. «Планирование стенда» ниже.
3. **Эффективность.** Минимум токенов и кругов ревью при том же качестве: харнес, который уже вёл соседнюю задачу (контекст, рабочая копия), лучше холодного; аудит и спецификацию без записи на стенд можно отдать любому свободному харнесу, реализацию с прогонами на стенде — тому, кто получит стенд первым.

Выбор и причину архитектор фиксирует в своём отчёте; перенос задачи на другой контейнер — тоже его решение.

### Синхронизация правил (`/updaterules`) — тоже зона архитектора

`/updaterules` в проектах архитектор запускает сам или поручает агенту — по своему усмотрению, без указаний владельца. Поводы: в шаблон слита правка, которая касается проекта; агент споткнулся о правило, уже исправленное в шаблоне; перед запуском новой задачи агента. Синхронизация идёт отдельной веткой и PR (`chore/updaterules-<дата>`), архитектор проверяет diff (затронуты только синхронизируемые файлы, `.dev.env`, `memory.md`, `USER-RULES.md`, `LLM-RULES.md`, `src/` не тронуты) и сливает сам. Рабочие копии уже идущих задач агентов не трогаются: агент подхватит правила при ребейзе на `main`; если новое правило нужно ему немедленно, архитектор пишет это в ответе агенту.

## Планирование стенда — зона архитектора

Очередность задач на общей тестовой базе архитектор решает сам, без согласования с владельцем: ставит в очередь, запускает параллельно или выносит на временную копию. Владелец задаёт только приоритеты и запреты. Архитектор учитывает их до отмены и согласует очередь с архитекторами соседних задач через доску задач (ниже), а не сообщениями между сессиями.

| Ситуация | Решение |
|---|---|
| Обе задачи только читают базу | Параллельно (`--force-parallel`), причина в промпте. |
| Блокировку держит задача, которая только читает (аудит, спецификация); вторая пишет в свои технические документы и загружает расширение | Допустимо параллельно (`--force-parallel`). В промпте писателя: чужие документы не трогать, расширение загружать минимальное число раз (в идеале один, на итоговой сборке), время загрузки — в протокол, чужие сеансы не завершать (только `question`). Архитектора читающей задачи предупредить заранее: что изменится в API после загрузки. |
| Две задачи пишут, особенно в одни объекты метаданных, регистры или модули, либо меняют настройки базы | Очередь. Если задача нужна раньше очереди — временная копия базы. |
| Нужна проверка обновления с прошлого релиза, разрушительный эксперимент или массовая запись | Временная копия базы. |

**Временная копия.** Создаётся через Devbox (`infobase_copy`) с публикацией, аналогичной исходной: HTTP-сервисы API и MCP данных, те же учётные записи API. Сразу после создания — запись на доске: `tools/task-board.sh claim <имя-копии> --holder <сессия> --issue <N> --ib <id базы> --pub <адрес>… --temp`. До запуска агента сними окно БСП «Информационная база была перемещена или восстановлена из резервной копии»: копия получила новую строку соединения, и первый интерактивный запуск (тонкий клиент, тесты в режиме Предприятия) ждёт решения в модальном окне — на #73 1c-integration-api-bp агент повис на нём. Штатный способ БСП — серверная процедура `РегламентныеЗаданияСервер.ЗаблокироватьРаботуСВнешнимиРесурсами()` (БСП 3.1, «Базовая функциональность»; то же, что кнопка «Это копия» в окне): выполни её на копии через `tools/dev-standalone/Invoke-DataMcp.ps1 code` или внешнее соединение. Решение сохраняется в базе, окно больше не открывается, а регламентные задания и обмены копии не ходят во внешние системы (переопределение `ПриЗапретеРаботыСВнешнимиРесурсами`). Если задаче нужны внешние ресурсы копии — `РегламентныеЗаданияСервер.РазблокироватьРаботуСВнешнимиРесурсами()`, и это решение архитектора с причиной в промпте. Проверка — запуск клиента копии с тайм-аутом без окна. В промпт агента — адрес копии и её `INFOBASE_PATH`. Копия создаётся под задачу и удаляется после успешной проверки: сначала снять публикацию, затем `infobase_drop`, затем `tools/task-board.sh release <имя-копии> --holder <сессия> --drop`. Идентификаторы базы и публикации архитектор записывает в отчёт и память до удаления. Копия не подменяет приёмку на основном стенде, если её требует DoD.

Решение и причину архитектор фиксирует в отчёте и на доске задач; архитекторы соседних задач видят его там.

## Доска задач — `tools/task-board.sh`

Одна доска на проект: `<основная копия>/.task-board/board.json`, вне git (путь в `.gitignore`). Сессии из рабочих деревьев пишут в тот же файл (основную копию скрипт находит через `git rev-parse --git-common-dir`), каждая запись идёт под `flock`. Доска заменяет согласование стенда сообщениями между сессиями.

- **Очередь работ:** issue, приоритет, архитектор-сессия, исполнитель (контейнер и харнес), стенд/база, состояние — `tools/task-board.sh set <issue> priority=1 architect=<сессия> executor=cursor1 harness=cursor stand=acc-demo state=working`.
- **Занятость стендов и временных копий:** id базы, публикации, кто держит и с какого времени — `claim <стенд> --holder <сессия> [--issue N] [--ib ID] [--pub URL] [--temp]`, `release <стенд> --holder <сессия> [--drop]`. Стенд занят другим — `claim` отказывает с кодом 1 и называет держателя: договариваешься с ним, а не загружаешь поверх.
- **Карточка задачи:** круги ревью, прогоны агента, время, токены и $ агента (если харнес их отдаёт), хотфиксы после релиза — `inc <issue> review_rounds|agent_runs|hotfixes`, `set <issue> tokens=… cost_usd=…`, `card <issue> [--markdown]`.

Правила:

1. **Перед запуском агента и перед загрузкой на стенд** — `tools/task-board.sh list`, затем `claim` стенда (или копии). После `agent-run` — `inc <issue> agent_runs`; каждый возврат агенту замечаний — `inc <issue> review_rounds`; хотфикс после релиза — `inc <issue> hotfixes` у исходной задачи.
2. **Освобождение:** после `committed`/`error` и загрузки релиза — `release`; удалённая копия — `release --drop`. Освобождает архитектор в своей основной копии: у агента в контейнере свой клон и своя доска, его `release` до доски архитектора не доходит (19.11.2026, #98 1c-integration-api-bp: агент «освободил» acc-demo, а доска архитектора держала стенд занятым).
3. **Закрытие issue:** карточка дублируется в комментарий issue — `tools/task-board.sh card <issue> --markdown` вставляется в закрывающий комментарий; затем `set <issue> state=closed`.
4. **Раз в неделю** — `tools/task-board.sh scorecard --days 7`: сводка по харнесам (задачи, ревью и прогоны на задачу, хотфиксы, часы, токены, $). Это основание для выбора исполнителя (критерий «Эффективность» выше); сводку архитектор кладёт в свой отчёт.

## Что положить в промпт запуска

Правило задаёт порядок работы, но не знает условий конкретной задачи. Тот, кто запускает агента, указывает в промпте:

- **Объём правок**, если он шире или уже правила «только `src/`»: документация API, каталоги, тесты.
- **Стенд и тестовые данные**: какая база, разрешено ли создавать собственные технические документы, что делать с очисткой, какие документы только читать.
- **Регрессию для выпуска**: какие тесты репозитория и какую коллекцию API-проверок прогнать и с каким выпуском сравнивать.
- **Принятые решения**, которые нельзя пересматривать, и ограничения (что не ослаблять, какие объекты метаданных запрещено добавлять).
  Запрет на права формулируй точно: «права на данные, RLS и профиль безопасности не менять». Право `Use` роли API на новый шаблон URL HTTP-сервиса — обязательная часть нового метода, без него метод недоступен роли и падает проверка прав; общий запрет «роли не менять» агент выполнить не может (1c-integration-api-bp #106).
- **Доска задач** живёт на хосте архитектора (`tools/task-board.sh` в основной копии): `claim`/`release` стенда делает архитектор до запуска и после приёмки. Агенту в контейнере доску не поручай — его копия скрипта пишет в доску контейнера, которую никто не видит (#106).
- **Форму сдачи**: PR или `change.patch`, артефакты, протокол.
- **Гейт релиза — обязательный пункт чек-листа приёмки**: «перед `review` — `tools/release-gate.sh --load` на голове PR, итог PASS; `out/release-gate.txt` — в отчёт, `out/release-gate.json` — в `<task-dir>/evidence/`; без отчёта гейта сдача в `review` не принимается» (`headless-agent.mdc` п. 5). Если нужен шаг на демо-базах актуальных версий БП — в промпт `--demo-bases <список>` (включается, когда в Devbox появятся инструменты обновления демо-баз и проект задаст `RELEASE_GATE_DEMO_CMD`; сейчас Фреш проверяет на БП 3.0.210.11 и 3.0.211.21, стенд — 3.0.210.8).

Регрессию проекта, отметку ограничений стенда и учёт своих тестовых данных правило требует и без промпта (п. 5). Промпт уточняет состав и базу сравнения: то, что выяснится только на приёмке, стоит лишнего цикла.

### Где агент запускает проверки

Тесты, регрессию, параллельные испытания и сборку headless-агент выполняет в своём контейнере dev-workplaces против назначенной ему (обычно временной) тестовой базы: `tools/designer-batch.sh` (CheckModules/CheckConfig с `-Extension`), vrunner, тесты репозитория, коллекция API, `cfe unload`. Каждый лог привязывается к SHA коммита. Требование «тесты только через Woodpecker» (skill `workstation-testing`) относится к рабочей станции владельца и на контейнер агента не распространяется (решение владельца 18.11.2026). Архитектор указывает это в промпте, чтобы агент не останавливался с вопросом.

## Промпт запуска

```
Ты разработчик. Загрузи .cursor/rules/headless-agent.mdc. Задача: openspec/changes/<id>/, Jira <KEY>, task-id <task>.
```

Подстановки: `<id>` — каталог изменения, `<KEY>` — ключ Jira, `<task>` — идентификатор для `agent-state`.

## Команды обёрток в контейнере

- `agent-state get <task>` — прочитать состояние.
- `agent-state set <task> <состояние> [--message-file F] [--pr URL] [--patch PATH] [--artifact PATH]...` — состояния `working`, `question`, `review`, `committed`, `error`.
- Каталог задачи: `$AGENT_TASKS/<task>` (по умолчанию `/home/dev/tasks/<task>`); сюда же идут `change.patch` и `out/`.

## Цикл

1. `working` — разработка по `tasks.md`.
2. `question` — агент остановился с вопросом; ответ приходит продолжением сеанса.
3. `review` — сдан PR или `change.patch` и отчёт; в базу и хранилище агент больше не пишет. До `committed` или `error` задача держит тестовую базу: один контейнер ведёт одну задачу за раз, а ту же базу другой контейнер не получит (блокировка по `INFOBASE_PATH` из `.dev.env`).
4. Приёмка: продолжением сеанса приходит строка `ПРИЁМКА: принято, зафиксируй`; замечания возвращают в `working`.
5. `committed` — помещение в хранилище (комментарий `<id> <KEY>`) или слияние, тег и релиз; сборки cf / cfe / epf в `<task>/out/`. Статус принимается только после приёмки (`agent-reply --accept`), иначе `agent-state` отвечает кодом 4. Если есть и хранилище, и репозиторий, сначала хранилище, затем слияние, тег и релиз; сбой одной половины — `error` с описанием сделанного.
6. `error` — неустранимая ошибка, причина в файле сообщения.

## Сопровождение архитектором

Архитектор (Claude или другой агент) отвечает за результат задачи и за то, сколько он стоит в токенах. Полномочия роли — что архитектор решает сам и что только с владельцем — задаёт ролевая инструкция [SVC-033-I](https://github.com/mikhailchuklay/1commerce-regulations/blob/main/SVC/SVC-033-I-tech-architect.md) в 1commerce-regulations (сессию к ней направляет правило `.cursor/rules/tech-architect.mdc`); разделы этого документа описывают процедуры. Задача — нужное качество за минимум ходов агента и своих.

- **Готовь рабочее дерево полностью.** `git worktree` не наследует неотслеживаемые файлы базового клона: копируй `.dev.env`, `.dsh/agent.env`, `.mcp.json` или `.codex/config.toml`, `AGENTS.local.md`. Без них агент работает без MCP (задачи #41 и хотфикс 1.48.1.1 в 1c-integration-api-bp).
- **QA MCP включён у каждого агента с парой QA.** Контейнер с парой (`onboard-agent.sh --with-qa`) видит `http://qa:8020/mcp`, но маршрут работает, только если: токен пары (`MCP_QA_HTTP_TOKEN` из `/data/compose/.env.qa-agent-<h><N>`) лежит в `~/.secrets/mcp.env` агента как `QA_MCP_TOKEN` и `ONEC_MCP_QA_TOKEN` (вносит владелец, SVC-033-I §4); `TOOL_QA` в `.dev.env` не `off`; харнесу прописан сервер — Cursor: `1c-qa` в `.cursor/mcp.json` (`Authorization: Bearer ${env:QA_MCP_TOKEN}`), Codex: `[mcp_servers.1c-qa]` с `bearer_token_env_var = "QA_MCP_TOKEN"` в `.codex/config.toml`, DSH: `ONEC_MCP_QA_URL=http://qa:8020/mcp` в `.dsh/agent.env` (без `ONEC_MCP_QA=off`). Проверка готовности: `tools/list` с токеном отдаёт инструменты `qa_*`/`ui_*`, без токена — 401. Без этого UI-сценарии и проверка типовых форм остаются «не проверено» (1.49.0.0 в 1c-integration-api-bp: пара QA была, маршрут выключен).
- **Общий стенд — не ниже последнего релиза.** Задачи на одном стенде выпускаются и параллельно: пока идёт твоя, main может уйти на релиз вперёд. Проверять задачу — на временной копии; на общий стенд загружается только ветка, которая содержит свежий `origin/main` и последний релиз, с версией выше выпущенной. Это проверяет `tools/stand-load-guard.sh`: агент запускает его перед каждой загрузкой на общий стенд (`headless-agent.mdc` п. 5), отказ — перебазироваться, а не обходить; `--allow "причина"` — только по слову архитектора, причина в протоколе. Перед `agent-reply`, который ведёт к загрузке, и перед приёмкой сверь то же сам (`git merge-base --is-ancestor origin/main <ветка>`). Хотфикс 1.49.1 после выпуска 1.50.0.0 откатил acc-demo для всех задач.
- **Номер версии — при слиянии, а не при старте.** Номер в промпте — предварительный. Перед слиянием: ветка содержит `origin/main`, тега с таким номером нет, номер — следующий от последнего релиза (новая функциональность — MINOR, хотфикс — PATCH). Хотфикс к выпуску, после которого уже вышел следующий, — PATCH от текущего main (1.50.1.0, а не 1.49.1.0). Кто сливает вторым, перебазируется и поднимает номер; архитекторов задач того же репозитория предупреди о занятом номере одной строкой.
- **После релиза — OpenSpec-изменение в архив.** Шаг готовности задачи, а не хвост: `openspec archive <id> --yes` (дельты переносятся в `openspec/specs/`, изменение — в `openspec/changes/archive/`) отдельным PR от свежего `origin/main`, слитым до закрытия issue. Делает агент при фиксации (`headless-agent.mdc` п. 7); не сделал — архитектор сам, сразу после релиза.
- **«Внесу после задачи» — сразу в карточку.** Обещанная доработка (своя, агента или side-сессии) в тот же ход становится issue или предложением сессии (карточкой) со ссылкой из отчёта; строка «сделаю потом» в отчёте без issue не считается.
- **После релиза — общий стенд на последний релиз.** Шаг готовности задачи: архитектор, выпустивший релиз, загружает релизную сборку на общий стенд проекта (тем же двухшаговым путём, после `tools/stand-load-guard.sh` на теге), проверяет версию и новые признаки (`GET /info` или аналог проекта) и пишет итог в отчёт и в комментарий к задаче. Если стенд держит чужая задача в `working`/`review` — договориться с её архитектором и загрузить сразу после неё. Архитекторам задач на том же стенде — одна строка: что изменилось в API.
- **Уборка — шаг готовности задачи, следишь ты.** Задача не закрывается (`committed` агента, закрытие issue), пока за ней остаётся мусор. Проверяешь сам при приёмке и после релиза, а не веришь отчёту:
  - **Временные копии баз** этой задачи удалены: публикации сняты, `infobase_drop`, `tools/task-board.sh release <копия> --holder <сессия> --drop`; на доске нет `--temp`-записей задачи. Удаление ждёт подтверждения владельца в Devbox — номер задания и подтверждения в отчёт и в напоминание владельцу в том же ходе; issue закрывается только с этой строкой, а после подтверждения проверяешь, что база действительно исчезла из `infobase_list`. Копию, которую передаёшь следующей задаче, перезаписываешь на доске на её архитектора — так она не теряется.
  - **Контейнер агента**: агент удалил явный мусор задачи — рабочее дерево `~/work/<task>` после слияния, временные каталоги сборки (`~/cfe-build-*`), выгрузки конфигурации и баз (`.dt`, `.cf`, XML-выгрузки типовой) в `~/tasks/<task>`. Остаются `report*.md`, `evidence/`, `out/` (релизная сборка), журналы прогонов. Проверка — `du -sh ~/tasks/<task> ~/work/<task>` в контейнере; больше сотен мегабайт без причины в отчёте — возврат агенту или уборка сам. Рабочие деревья убирает `tools/agent-workspace-cleanup.sh [--apply] <контейнер>` (по умолчанию — план): он удаляет только git worktree в `~/work`, ветка которых влита в `origin/main` или запушена, пропускает деревья активных задач (`agent-state` working/question/review), каталоги с живыми процессами, клоны и всё вне `~/work`, а незакоммиченное сохраняет патчем в `~/tasks/<каталог>/`. Каталоги закрытых задач, оставшиеся от прошлых сессий, убираешь тем же скриптом сам: **уборка мусора — зона архитектора, владельцу на согласование не выносится** (решение владельца 19.11.2026). Блок режима auto на ad-hoc `rm -rf` — повод взять скрипт, а не спрашивать владельца. Подтверждение владельца остаётся только там, где его требует сама система (удаление базы в Devbox).
  - **Тестовые данные на стенде** — по списку GUID агента помечены на удаление (`headless-agent.mdc` п. 5), сверено чтением.
  - **Сторонние эталонные базы** (пустая БП нужной версии для сверки и т. п.) — по тем же правилам, что временные копии.
  Повод: 18.11.2026 общий том `/data` контейнеров заполнился на 99 % — выгрузки БП по 4,9 ГБ из давно выпущенных задач лежали в контейнерах, временная IB 79 жила после релиза, потому что подтверждение удаления ждали без напоминания.
- **Внешнее действие подтверждается ответом получателя, а не своим статусом.** Отправка в банк, ЭДО, письмо, загрузка в чужую систему считается выполненной только по ответу или квитанции получателя (статус банка «принят»/«исполнен», квитанция ЭДО, идентификатор во внешней системе). Локальный статус («Отправлен в банк», «Отправлено») — только то, что вызов ушёл. В промпт агента пиши, какой ответ получателя считается доказательством и сколько его ждать; без него агент ставит `question`, а не продолжает сценарий и не сообщает «отправлено». Повод: #76 1c-integration-api-bp — платёжка на 1 ₽ «отправлена» по статусу копии, а в банке её не оказалось.
- **Сначала проверь исполнителя.** До старта задачи или side-сессии посмотри, не ведёт ли её уже агент: `agent-state get <task>` в контейнерах и реестр блокировок. В брифе любой сессии пиши строку «исполнитель: <контейнер>/<task> | нет». Без этого две сессии делают одну правку дважды (хотфикс 1.48.1.1: бриф «восстанови функцию» ушёл в сессию, пока задача уже шла на dsh1).
- **Следи сам, а не жди статуса.** После `agent-run` поставь фоновое ожидание `tools/agent-monitor.sh --exit-on-idle <контейнер> <task> <N> <рабочее-дерево>` фоновой командой Bash (`run_in_background`), а не инструментом Monitor: у Monitor лимит 30 минут, и долгую задачу приходится перезапускать (15 перезапусков в #41 1c-integration-api-bp). Фоновая команда будит архитектора, когда скрипт выходит: код 0 — состояние `review`/`question`/`error`/`committed`, код 3 — первый простой (посмотри на агента и запусти монитор снова). Скрипт бери из `tools/` своей рабочей копии, а не копией во временной папке: временная копия отстаёт от шаблона. Сигналы: смена состояния или простой дольше N минут (файлы рабочего дерева и `~/tasks/<task>` не менялись, нет процессов `1cv8`/`vrunner`). Рост `run-N.log` — не признак: Cursor с `-p --output-format json` пишет лог только в конце прогона (ложный простой в задаче #43 1c-integration-api-bp). Смотри хвост JSONL (последние вызовы и мысли), а не весь лог: полный лог — сотни килобайт контекста.
- **Вмешивайся сразу.** Агент ищет то, чего нет в среде, гоняет одну и ту же проверку, ждёт модальное окно, ушёл за объём задачи — ответь или исправь среду, не дожидаясь `review`. Правку, которая перезапускает идущий прогон (образ, окружение контейнера), применяй после его завершения.
- **Закрывай причину, а не случай.** Каждое трение (недоступный инструмент, неясное правило, ложный «PASS») — правка окружения, инструмента или промпта сразу, правки шаблона по итогам задачи — PR, который архитектор сам проверяет и сливает (ниже, «PR задач — твои»), правки общего регламента 1commerce-regulations — предложением владельцу как менеджеру процесса: проблема → доказательство из прогона → правка → экономия.
- **Ретро — шаг приёмки, без команды владельца.** При приёмке каждой задачи (до слияния) и при её закрытии просмотри протокол: вопросы агента, круги ревью, упавшие прогоны, отказы инструментов, обходы. Каждое трение — правка сразу (промпт, инструмент, шаблон — PR, который сливаешь сам; devbox/инфраструктура — issue в их репозитории); в отчёт задачи — строка «Ретро: трение → правка/issue» или «Ретро: трений нет». Владелец не должен спрашивать, что улучшить (19.11.2026).
- **Подтверждения Devbox живут около двух часов.** Удаление базы и другие подтверждаемые задания ставь, когда владелец на связи, номер подтверждения — в тот же ход. Истекло (`approval истёк (TTL)`) — перезапроси сам и сообщи новый номер, а не повторяй старый (19.11.2026: 804 и 808 истекли до клика).
- **После перезапуска приложения фоновые мониторы умирают.** Первым ходом после перезапуска проверь `agent-state` своих задач и перезапусти `tools/agent-monitor.sh`; «working» без монитора — слепая зона (19.11.2026, #98 и #101).
- **Отклонить замечание валидатора как ложное — только с воспроизведением.** Покажи вход, на котором замечание не срабатывает; без этого замечание — дефект. 19.11.2026, #98: «параметр не установлен» отклонили как ложное, а это был 500 на нулевом UUID.
- **Схема MCP в клиенте может отстать от сервера.** После выкатки нового параметра у уже запущенной сессии клиент шлёт его строкой (422 на массиве), Reconnect помогает не всегда. Проверь `tools/list` сервера напрямую; если там поле есть — вызови `tools/call` по HTTP с тем же токеном, а не жди перезапуска (19.11.2026, devbox `inet`).
- **Лимит или баланс харнеса — блокер исполнителя, а не задачи.** `QUOTA`/`Insufficient Balance`/`LIMIT` в `run-N.log` — сразу сообщение владельцу одной строкой (пополнение — его действие) и выбор другого свободного контейнера; задача держит стенд и ждёт.
- **Улучшай по своей инициативе, не спрашивая.** Если считаешь улучшение верным (инструмент, обёртка, скрипт, правило или процедура шаблона, промпт), делай его сам без поручения и без согласования с владельцем: правка, PR, ревью, слияние, `/updaterules`. Не предлагай владельцу карточкой то, что вправе сделать сам. Объёмную правку или правку вне текущей задачи веди в отдельной сессии со своей веткой и PR, чтобы не задерживать задачу. Решение, которого нет в перечнях SVC-033-I, принимаешь сам и записываешь в отчёт с причиной.
- **Приёмка по существу.** Ты владелец кода: ревью PR (корректность, транзакции и блокировки, контракт, тесты) и сверка доказательств с SHA; «зелёный» без командной строки и лога не принимается.
  - **Отчёт гейта сверяется механически, проверки не перезапускаются.** `release-gate.json` агента: `sha_head` = голова PR (`gh pr view --json headRefOid`), `result` = PASS и все шаги PASS (ни одного `SKIPPED`), `loaded_by_gate` = true либо в отчёте объяснено, чем загружена база, `cfe_sha256` = файл релиза — после публикации скачай актив релиза (`gh release download <тег> -p '*.cfe'`) и сверь `sha256sum`. Актив загружай под латинским именем `<тег>.cfe` (копия сборки гейта, тот же sha256): кириллическое имя `<EXTENSION_NAME>-<версия>.cfe` GitHub превращает в нечитаемое вида `1._.API_.-1.55.0.0.cfe` (19.11.2026, 1.55.0.0 1c-integration-api-bp). В релиз идёт та самая сборка гейта (`out/<EXTENSION_NAME>-<версия>.cfe`) без пересборки; новый коммит после приёмки — новый прогон гейта. Любое расхождение — возврат агенту без собственных прогонов: из 11 релизов 17–18.11.2026 три потребовали хотфикса, потому что агент сам собирал командные строки проверок и сообщал PASS (1.48.1.0 — `/CheckModules` без `-Extension`, 1.49.0.0 — форма не проверена, 1.51.1.0 — блокер анализатора).
  - **Матрица приёмки** — в комментарии ревью PR: каждый сценарий дельта-спецификации → доказательство (команда, лог, SHA) или «не проверено» с причиной. Сценарий без строки матрицы — не принят.
  - **Типовое сначала.** Решение, которое опирается на типовой механизм БП/БСП (проведение, регистр, обработчик, общий модуль), ссылается на модуль:строку выгрузки типовой той версии, на которой проверялось. Без ссылки — замечание в ревью, а не приёмка. Раздел «Валидаторы» отчёта `agent-state` сверяй с протоколом построчно: блокер валидатора, отложенный в протоколе «до решения владельца» или «в следующий патч», — не приёмка, а замечание (1.49.0.0: блокер `syntaxcheck` был только в протоколе, отчёт называл валидатор недоступным). «Не проверено» по инструменту, который можно починить в среде, тоже не принимается: сначала чинишь среду, потом прогон.
- **PR задач — твои: проверяешь и вливаешь сам.** Все PR, которые появились при выполнении задач разработки, идущих через архитектора, — его ответственность, и владельца он не ждёт. Сюда входят PR агентов, side-сессий, правок правил и шаблона по итогам задачи. Порядок такой:
  1. Ревью diff по существу и сверка доказательств: командные строки, логи, SHA.
  2. Чистка мусора (байткод, протоколы агента в корне).
  3. Комментарий ревью в PR.
  4. Слияние. В репозитории с ruleset «review для внешних PR» — через исключение владельца (`gh pr merge --admin`).
  5. Если менялся шаблон — `/updaterules` в проектах-потребителях.
  PR людей и сессий вне задач архитектора — только по слову владельца. Тег и релиз — по регламенту релиза задачи.
- **Закрытие задачи — тоже твоё.** После релиза архитектор сам закрывает issue задачи с коротким комментарием: релиз, PR, что осталось непроверенным, карточка задачи с доски (`tools/task-board.sh card <issue> --markdown`). Непроверенное идёт в описание релиза, а реальная доработка — в новую задачу; issue «на решение владельца» открытым не оставляется. За владельцем остаются только действия из SVC-033-I, требующие согласия (Фреш и каталог, рабочие базы, секреты, массовые записи на общем стенде, утверждение общего регламента).

## Инструменты базы и хранилища (vanessa-runner)

В Linux-контейнере агента есть PowerShell 7 (`pwsh`, образы `onec-agent-cursor` и `onec-desktop` с 09.11.2026): инструменты правки метаданных скилла `1c-metadata-manage` (`cfe-*`, `cf-*`, `form-*`, `meta-*`, `skd-*`, `role-*`, `mxl-*`) запускаются как `pwsh -NoLogo -NonInteractive -File <скрипт.ps1> …` с теми же параметрами, что на Windows; результаты прогона — `docs/linux-compat.md`. Не работают на Linux только скрипты, которые запускают `1cv8.exe` по Windows-путям: `db-*`, `epf-build`, `epf-dump`, `stub-db-create` (`1c-metadata-manage`) и `repo-ops.ps1` (`1c-repository-manage`). Их заменяет vanessa-runner 3.x: MCP-сервер `vrunner` в `.cursor/mcp.json` (в шаблоне выключен, в контейнере включается: `"disabled": false`) и та же утилита в оболочке, `xvfb-run -a vrunner …` (платформе нужен виртуальный экран).

Параметры подключения агент не задаёт сам: `agent-run` выставляет их из `.dev.env` проекта и файлов `~/.secrets` контейнера. Уже заданные переменные не перезаписываются.

| Переменная vrunner | Откуда |
|---|---|
| `VRUNNER_IBCONNECTION` | `INFOBASE_PATH`: при `INFOBASE_KIND=server` `сервер:порт/база` → `/Sсервер:порт\база`, иначе `/F<путь>`; значение, начинающееся с `/F` или `/S`, берётся как есть |
| `VRUNNER_V8VERSION` | имя каталога `PLATFORM_PATH` (`/opt/1cv8/x86_64/8.5.1.1343` → `8.5.1.1343`) |
| `VRUNNER_DBUSER` / `VRUNNER_DBPWD` | `IB_USER` / `~/.secrets/ib-password` |
| `VRUNNER_STORAGE_NAME` / `_USER` / `_PWD` | `REPOSITORY_PATH` / `REPOSITORY_USER` / `~/.secrets/storage-password` |
| `VRUNNER_EXTENSION_NAME` | `EXTENSION_NAME` |

Пароли в `.dev.env` контейнера не пишутся: `IB_PASSWORD` и `REPOSITORY_PASSWORD` оставить пустыми.

### Загрузка расширения только через Конфигуратор

Для vanessa-runner 3.0.2 загрузка из XML или `.cfe` выполняется в два шага. Запускать в окружении агента, где уже заданы параметры `VRUNNER_*`. `EXTENSION_NAME` и `SOURCE` ниже задаются явно из параметров проекта и выбранного источника:

```bash
: "${EXTENSION_NAME:?Нужно имя расширения}"
: "${SOURCE:?Нужен каталог исходников или файл .cfe}"
xvfb-run -a vrunner cfe load --no-update-db --extension-name "$EXTENSION_NAME" "$SOURCE" &&
  xvfb-run -a vrunner infobase update --target "$EXTENSION_NAME"
```

Первый шаг только загружает конфигурацию расширения. Второй применяет её к БД, только если первый завершился успешно. Не передавать второму шагу `--src`, пустой `--target` или `--ibcmd`. Это не запуск обработчиков обновления БСП: если они нужны, их выполнение остаётся отдельной операцией.

Обычный `cfe load` после обновления БД безусловно запускает Предприятие для изменения свойств расширения — отсутствие флагов свойств не предотвращает этот запуск. В двухшаговом варианте этот участок пропускается. Активность, безопасный режим и защита от опасных действий этим способом **не устанавливаются**; для нового расширения проверять их отдельно. Не подменять проверку свойств утверждением, что переданные при загрузке `--active` или `--safe-mode` сработали: с `--no-update-db` они не применяются.

MCP-эквивалент: `cfe_load` с параметром пропуска обновления БД и явным именем расширения → успешный `task_result` → `infobase_update` с `target`, равным имени расширения. Имена и типы аргументов брать из текущей схемы инструментов, а не переносить написание CLI-флагов наугад; если нужных аргументов нет — использовать CLI выше.

Ошибка обновления (например, пересечение идентификаторов с OneMCP) означает, что расширение не применено к БД, даже если загрузка исходников прошла. Остановиться и сохранить лог, без повторов и без запуска тонкого клиента.

Ограничения, проверенные на БП 3.0 / 8.5.1:

- Операции Конфигуратора (загрузка и выгрузка, обновление БД, хранилище, сборка) идут без окон только на виртуальном экране (`xvfb-run -a`, `tools/designer-batch.sh`) и с `/DisableStartupDialogs`. Без этого окно ошибки открывается на экране сеанса и процесс ждёт нажатия OK. Если контейнер — рабочее место человека, окно появляется у него (08.11.2026: выгрузка по `-listFile` в пустой каталог, «объект метаданных не существует»).
- Операции Предприятия (список и проверка расширений, тесты YAxUnit/Vanessa, свойства расширения после загрузки) могут зависнуть на модальном окне БСП: «Предупреждение безопасности» при первом входе пользователя с правом открывать внешние обработки, окна первого запуска после изменения конфигурации. vanessa-runner формирует `/C` сам и не передаёт `ОтключитьЛогикуНачалаРаботыСистемы` (issue vanessa-opensource/vanessa-runner#378). Первый вход пользователя агента делает человек и закрывает окна.
- MCP-инструменты `cfe_*` (vrunner 3.0.2) не берут имя расширения из `VRUNNER_EXTENSION_NAME` и без явного `extension_name` работают с основной конфигурацией: `cfe_unload` выгрузил всю конфигурацию БП вместо расширения. Утилита в оболочке переменную учитывает. Правило агента требует передавать имя явно.
- Прерванный запуск оставляет сеанс в кластере, который блокирует обновление БД: после тайм-аута завершать свои сеансы.

### Пакетный Конфигуратор: `tools/designer-batch.sh`

Инвариант для любой среды: процессы `1cv8` / `1cv8c`, запущенные агентом, не используют дисплей человека и не ждут диалог.

| Среда | Как выполняется |
|---|---|
| Windows | `Start-Process -WindowStyle Hidden` + флаги (рецепт `designer-batch-checks.mdc`) |
| Linux с X-сеансом | только `xvfb-run -a` или свой `Xvfb`; `DISPLAY` сеанса не используется |
| Linux без X | `ibcmd` или `vrunner` под `xvfb-run -a`; без виртуального экрана Конфигуратор не запускается |

Флаги `/DisableStartupDialogs /DisableStartupMessages /Out /DumpResult` и тайм-аут обязательны всегда. Предпочтение: `ibcmd` → `vrunner` → `tools/designer-batch.sh`. Прямой вызов `1cv8` без обёртки запрещён.

```bash
tools/designer-batch.sh -- /CheckModules -ThinClient -Server -ExternalConnection -Extension "$EXTENSION_NAME"
tools/designer-batch.sh --timeout 1800 -- /DumpConfigToFiles "$DUMP_DIR"
```

Обёртка берёт платформу, базу и пользователя из `.dev.env` (запасной вариант — `VRUNNER_*`), запускает Конфигуратор на своём виртуальном экране (`xvfb-run -a`, иначе свой `Xvfb`; первый номер — `DESIGNER_XVFB_FIRST`, по умолчанию 99), снимает `WAYLAND_DISPLAY`, по тайм-ауту (`--timeout`, `DESIGNER_TIMEOUT`, по умолчанию 600 с) гасит только свою группу процессов. Вердикт — по трём сигналам: код возврата, `/DumpResult`, текст `/Out`. Коды: 0 — успех, 1 — не прошло или тайм-аут, 2 — запуск отклонён, 3 — нет виртуального экрана. Отклоняются: больше одной пакетной команды, ключи подключения и вывода в аргументах, запрещённые операции (`/EraseData`, `-AllExtensions`, `/DeleteCfg` без имени, `-disableSupport`, `/IBCheckAndRepair`), частичная выгрузка без полной в том же каталоге. `--dry-run` показывает команду со скрытым паролем, `--self-test` проверяет разбор лога.

## Применение патча на стороне архитектора

Патч делается как `git add -A && git diff --cached --binary > change.patch`, поэтому содержит новые файлы и бинарные изменения. Применять к «было» (чистая выгрузка или основная ветка):

```
git apply --index --binary change.patch
```

`--index` переносит изменения и в индекс (новые файлы попадут в коммит). Бинарные блоки разбираются из патча, сделанного с `--binary`. Проверка без применения: `git apply --check change.patch`.

## Файлы

`tools/agent-workspace-cleanup.sh` — уборка рабочих деревьев агентов в контейнере: план по умолчанию, `--apply` — удалить, `--keep <каталог>` — не трогать. Удаляет только влитые или запушенные git worktree в `~/work` вне активных задач; незакоммиченное — патчем в `~/tasks/<каталог>/`; печатает `du -sh ~/work` до и после. Те же `AGENT_SSH_HOST`, `AGENT_CONTAINER_PREFIX`, `AGENT_EXEC_USER`. Разреши его в `permissions.allow` проекта (`Bash(tools/agent-workspace-cleanup.sh:*)`), чтобы режим auto не останавливал уборку.

`tools/agent-monitor.sh` — фоновое ожидание архитектора по задаче агента: печатает смену состояния и однократное предупреждение о простое, завершается на `review`/`question`/`error`/`committed`, переживает обрыв ssh. Только чтение. ssh-алиас и префикс контейнера задаются `AGENT_SSH_HOST`, `AGENT_CONTAINER_PREFIX`; `--once` — один замер.

`tools/agent-monitor.sh --exit-on-idle` — выход с кодом 3 при первом простое; так фоновая команда Bash будит архитектора и при зависшем агенте.

`tools/release-gate.sh` — гейт релиза агента перед `review`: фиксированные командные строки проверок, отчёт `out/release-gate.json` и `out/release-gate.txt` (SHA HEAD, sha256 сборки, команда, код возврата и хвост лога каждого шага, итог PASS/FAIL), логи в `out/release-gate/`. Коды: 0 — PASS, 1 — FAIL, 2 — ошибка запуска.

`tools/task-board.sh` — доска задач проекта (очередь, стенды и копии, карточки, недельная сводка); файл `<основная копия>/.task-board/board.json` вне git, запись под `flock`.

`.gitattributes` приводит переносы строк к виду платформы (`*.bsl`, `*.xml` — CRLF) и скрывает `ConfigDumpInfo.xml` из diff, чтобы разница на приёмку содержала только значимые правки.
